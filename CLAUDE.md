# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

DEARLY — Our Little Home (Korean display name: "디어리 — 우리의 작은 집", renamed from "Our Little Life"): a free web app where a user registers two characters (image + traits), decorates a home, watches the characters live together, and saves the scene as a PNG. Static site, no backend, deployed to GitHub Pages. Internal identifiers (localStorage keys, the `dearly-our-little-life` package name, file/component names) were deliberately **not** renamed to match — only user-facing display text changed. Don't rename storage keys or the package name just because the display name changed; that would orphan existing users' saved data for no reason.

Stack: React 19 + TypeScript + Vite 8, PixiJS 8 (canvas rendering, currently dormant — see below), Zustand 5 (state).

## Architecture

### App flow is phase-based, not routed

There is no router. `src/app/uiStore.ts` holds `phase: 'setup' | 'decorate' | 'live'`, and `src/app/App.tsx` renders a different screen based on it. `setup` (`SetupScreen`) and `decorate` (`DecorateScreen`) are implemented; `live` is still a placeholder. As features land, replace the remaining placeholder with the real feature component rather than introducing routing.

### State: one Zustand store per domain, not one global store

- `src/app/uiStore.ts` — which phase is active.
- `src/features/character/characterStore.ts` — up to `MAX_CHARACTERS` (5, `CharacterForm.tsx`) characters (name, image, traits, persona/tone profile). **Persisted** (see its own section below).
- `src/features/home/homeStore.ts` — **up to `MAX_ROOMS` (5) independently-decorated rooms** (`rooms: Room[]`), plus `activeDecorateRoomId`/`activeLiveRoomId` (which room each screen currently shows) and the UI-only `selectedFurnitureId`. **Persisted** (see below). See "Multi-room support" below for the full room data model.
- `src/features/simulation/simulationStore.ts` — `isRunning` is a genuine global pause/resume flag, shared across *every* room at once (not per-room): `LiveScreen.tsx` calls `start()` on mount and toggles it with a 재생/일시정지 button. Both `useCharacterMovementSimulation.ts` and, through it, the auto-dialogue trigger honor it. `tick` is still unused.
- `src/features/simulation/characterMovementStore.ts` — **not persisted**, runtime-only per-character movement/room state (`roomId`, `x`/`y`, `destination`, `destinationRoomId`, `currentBehavior`, `status`), keyed by character id. See "Character movement, collision, and encounter detection" and "Multi-room support" below.
- `src/features/dialogue/dialogueFrequencyStore.ts` — persisted `mode` (5 values, default `'normal'`), the "대화 빈도" setting on the Live screen.
- `src/features/dialogue/relationshipStore.ts` — persisted, **per-pair** (`relationshipsByPair`, keyed by `pairKey.ts`) since there can be up to 10 pairs among 5 characters, plus a `defaultRelationshipType` fallback for any pair without an explicit setting.

A feature's store, types, and components live together under `src/features/<feature>/`. Cross-cutting UI-only state goes in `src/app/`.

### The room is DOM + SVG, not PixiJS — the canvas engine is dormant, reserved for `live`

Early on this project used PixiJS to render furniture as canvas sprites. That was replaced: furniture, the room, and its decorations are now plain React components rendering inline SVG, styled with CSS (`src/features/home/`). This reads far better for hand-illustrated pastel furniture than PixiJS primitives did, and made iterating on the art fast.

`src/engine/` (`SceneEngine.ts`, `useSceneEngine.ts`, `export/capturePng.ts`) still exists but **nothing currently imports it** — it's kept for the future `live` phase, where character animation genuinely needs its own render loop independent of React's render cycle (the original rationale still holds for *that* use case). Don't route new home-decoration work through it; follow the DOM/SVG pattern below instead. If `live` ends up going DOM/CSS-animation instead of PixiJS too, this folder should be deleted rather than kept as unused scaffolding.

### The room has a fixed logical coordinate system, decoupled from its rendered pixel size

`src/features/home/roomLayout.ts` defines `ROOM_WIDTH`/`ROOM_HEIGHT` (720×440) — a fixed logical space that `FurniturePlacement.x`/`y` are stored in. `Room.tsx` renders at `aspect-ratio: 720/440` and `width: 100%`, and `FurnitureItem.tsx` positions/sizes itself with **percentages** of that box (`left: (x/ROOM_WIDTH)*100%`, etc.), not pixels. This is why the same saved layout looks identical whether the room renders at 400px or 900px wide — resizing the browser never touches the stored coordinates, only the CSS box they're a percentage of.

The one place raw pixels still matter is **during a drag**: pointer movement arrives in real screen px, so `FurnitureItem`'s drag handler reads the room's current `getBoundingClientRect()` to compute a px→logical scale factor before applying the delta to `placement.x`/`y`. `clampToRoom()` (same file) keeps a placement's effective footprint (`width * scale`, `height * scale`) fully inside `[0, ROOM_WIDTH] × [0, ROOM_HEIGHT]`; both the properties panel's X/Y inputs and the drag handler clamp through it. In tests, jsdom reports `getBoundingClientRect()` as all zeros (no real layout engine) — the scale factor falls back to `1` in that case rather than dividing by zero.

### Furniture: catalog vs. placement, and illustrations that branch by type

`src/features/home/types.ts` splits furniture into two shapes on purpose:

- `FurnitureDefinition` (`furnitureCatalog.ts`) — what a type of furniture *is*: base `width`/`height` (in room-logical units), `category`, `minScale`/`maxScale`, and `interactionSlots`.
- `FurniturePlacement` (per-instance, lives in `homeStore.furniture`) — where one instance sits: `x`/`y`/`scale`/`rotation`/`colorway`/`layer`.

Rendering branches by `furnitureId` through `FurnitureIcon` (`illustrations/index.tsx`), a plain `switch` returning the matching `<XIllustration>` — deliberately *not* a `furnitureId → Component` lookup map used as a JSX tag, because oxlint's `react/no-unstable-components`-style check (correctly) flags a component reference resolved during render as JSX. Each `<XIllustration>` (`illustrations/*.tsx`) draws itself entirely in fractions of its own `width`/`height` props (not fixed px) so the same silhouette stays correctly proportioned at any catalog size — comments in `SofaIllustration.tsx`/`BedIllustration.tsx` call out that their cushion/pillow-center fractions are exactly what `sofa-left`/`sofa-right`/`bed-left`/`bed-right`'s `interactionSlots` offsets in `furnitureCatalog.ts` were derived from; if you change those fractions, update the offsets too. Colors come from `colorways.ts` (2 presets per furniture type, built from the shared tokens in `palette.ts`), selected per-placement via `FurniturePlacement.colorway`.

### Furniture catalog expansion (phase 2): 40 pieces, category/zone/collision on the definition

`furnitureCatalog.ts` now has the six original entries first (ids, names, sizes, slots unchanged — saved placements refer to them) plus 34 new ones (거실/침실/주방/서재/조명/장식/창문·러그). New `FurnitureDefinition` fields (`types.ts`): `category` (`living|bedroom|kitchen|study|lighting|decor|windowRug`, replacing the old `seating|table|bed|decor|wall`), `zone` (`floor|wall`), `collision` and `isFreeDefault` (all free; no price/ownership data exists yet). Existing `sofa` is the 2-seater, `bed` stays "침대", `table` stays "테이블"; `bed-single`/`bed-double`/`dining-table`/`coffee-table` are separate ids. TV and its stand are one piece (`tv-stand`).

- **Illustrations** live in `illustrations/{Living,Bedroom,KitchenStudy,Prop}Illustrations.tsx` with shared primitives in `illustrations/parts.tsx` (`Block`, `Leg`, `Tabletop`, `GroundShadow`, …). `FurnitureIcon` stays a plain `switch`, and the catalog card, properties preview, decorate room and live room all render through it, so a piece looks identical everywhere. Each pieces' `groundY`/frame bottom is the single source its legs and its `GroundShadow` key off (tested: shadow within 4.5% of the drawing height of the lowest structure). New pieces use the shared two-tone `GENERIC_COLORWAYS` (`colorways.ts`, `main`/`accent`); per-part color and patterns are the next phase.
- **Collision is per definition, not per id** (`movementEngine.ts`'s `furnitureObstacles`): `{mode:'none'}` never blocks (rug, window, all wall decor, tabletop props); `{mode:'solid', footprintHeightRatio}` blocks a rectangle anchored to the bottom of the drawing, so wardrobes/fridges/shelves block only their base. Original solid pieces keep their full rectangles; `window` became non-blocking; an id missing from the catalog still blocks a 60×60 square.
- **Wall pieces** (window, clock, frame, mirror, curtain) only *start* in the wall band (`placementDefaults.ts`); after that they move freely anywhere with no snapping or range limit.

#### Part colors and surface patterns (phase 3, schema v4)

- **Data**: `FurnitureDefinition.colorParts` (recolorable parts, display order) and `patternSurfaces` (fabric surfaces only — never legs/handles/frames/shadows) are declared per piece in `furnitureCatalog.ts`'s `STYLING` table (sofa 본체/방석/다리, bed 헤드보드/프레임/이불/베개, table 상판/다리, chair 좌판/등받이/프레임, cabinet 본체/문/손잡이, …; plant/rug/window declare none yet). A placement gains **optional** `colors` (`partId → #rrggbb`) and `patterns` (`surfaceId → {type, baseColor, color, size 1|2|3}`) — absent until the user customizes, so untouched placements are byte-identical to before. `furnitureStyle.ts` holds the types, the 12 pattern types (`solid` = remove), the validators (`normalizePartColors`/`normalizePatterns`, `undefined` when empty) and `toneFromHex` (outline = fill × 0.86).
- **One source of default part colors**: `furnitureStyling.ts`'s `PART_DEFAULTS` (per furniture id, from the preset `colorway`) is read by *both* the illustrations and the editing panel, via `resolvePartTones(id, colorway, style)`. The original sofa/table/bed derive theirs from their own preset tables, so defaults look exactly as before. Part ids there must match the catalog's `colorParts` (tested), and a pattern surface's id must also be a part id (a new pattern starts tone-on-tone with that part).
- **Rendering**: illustrations take `style?: FurnitureStyle`; a patterned surface is `fill="url(#…)"` on just the shapes that are that fabric (`surfacePattern`/`patternFill` in `illustrations/surface.ts`), with the `<pattern>` in that SVG's own `<defs>` (`Svg` in `parts.tsx` → `patterns/furniturePatterns.tsx`; motifs reuse `getWallpaperPatternContent` where the shape matches). **Pattern ids**: `FurnitureIcon` calls `useId()` once per rendered piece and prefixes every id with it (sanitized), so any number of pieces/previews never collide. Uncustomized pieces emit no `<defs>` at all.
- **UI**: `FurnitureStyleEditor.tsx` (mounted in `FurniturePropertiesPanel`, keyed by placement id) shows only the selected piece's parts/surfaces, reusing `ColorSwatchPicker` (now with a `presets` prop; `FURNITURE_COLOR_PRESETS` = the 16 wallpaper/floor presets + 세이지 그린 + 브라운, plus the native free color input) and writes straight to the store (`updateFurniture` now accepts `colors`/`patterns` and re-normalizes).
- **Migration**: `homeStore` `SCHEMA_VERSION` is **5**. `migrate` no longer returns early at v3; every path ends in explicit `version < 4` (`migrateRoomToV4`, colors/patterns) and `version < 5` (`migrateRoomToV5`, `variant`) steps that re-validate placements' newer keys and touch nothing else. `merge` normalizes on load too.

#### Furniture color palette (dark colors added; still schema 5, no migration)

- **One list, `colorPresets.ts`**: `FURNITURE_COLOR_GROUPS` = 밝은 색상 (exactly the previous furniture set: 16 wallpaper/floor presets + 세이지 그린 + 브라운, same ids/hex/order) / 회색·검정 (라이트 그레이, 그레이, 차콜, 소프트 블랙, 블랙) / 빨강·와인 (레드, 딥 레드, 와인, 버건디) / 기타 진한 색상 (네이비, 딥 브라운, 포레스트 그린, 플럼); `FURNITURE_COLOR_PRESETS` is their flattening. Part colors, pattern background and pattern motif pickers in `FurnitureStyleEditor` all pass `groups={FURNITURE_COLOR_GROUPS}` to `ColorSwatchPicker` (which gained an optional grouped mode; wallpaper/floor still use the flat `SURFACE_COLOR_PRESETS` and are unchanged). Never copy a list into an editor.
- **Outlines adapt to the fill** (`furnitureStyle.ts`'s `toneFromHex`): light/pastel fills keep the darker outline (×0.86, as before); fills with luminance < 0.3 get a *lighter* outline (mixed 30% toward white) so a black/burgundy body keeps visible edges while legs (wood), handles (metal) and shadows keep their own tones. A new pattern starts tone-on-tone with the part's (adaptive) outline color, so it is readable on dark parts; background and motif are independent.
- **Whole-piece dark presets** (`colorways.ts`'s `DARK_COLORWAYS`: 차콜/블랙/레드/와인/네이비/딥 브라운, hex read from the palette by id) are *appended* after every piece's existing colorways (sofa/table/bed/rug/window/generic; the plant gets 포레스트 그린), so every original id, order and default (`rose`/`natural`/`blush`/`sage`/`blush`/`cream`, generic `cream`) is unchanged.
- **Rug border** is now its own part (`border`, 러그 테두리): unless the user picks one it *follows the face* (`furnitureStyling.ts`'s `FOLLOWS` — the border is the face's outline color, exactly the original look), and choosing one detaches it; it colors the rug's edge and inner ring.

#### Rug and window (phase 4) reuse the same system

- **Same declarations, no special cases**: the rug declares `colorParts: [base]` and `patternSurfaces: [base]`; the window `[frame, curtain]` with `curtain` patternable (both in `furnitureCatalog.ts`'s `STYLING`, defaults in `furnitureStyling.ts` — the rug's `base` from `RUG_COLORWAYS`, the window's frame the original `#fbf3e4/#e8d9bb`, curtain from `WINDOW_COLORWAYS`). They are edited by the very same `FurnitureStyleEditor`, stored in the same `colors`/`patterns` maps, and rendered through `resolvePartTones`/`surfacePattern`. Untouched rug/window SVG is exactly the original (tested against the old geometry).
- **Rug pattern = the whole face**: the pattern fills the rug's face shape edge to edge and the faint inner "woven border" ring is stroked on top (never patterned). Rug tiles use `RUG_PATTERN_TILE_SCALE` (2×, via `surfacePattern(surface, style, tileScale)` → `SurfacePattern.tileScale` → `FurniturePatternDef`) on top of the 작게/보통/크게 step so motifs read at the rug's scale.
- **Shapes (`variants`)**: a definition may list `variants` (`{id,label,width,height}`, default first). The rug has 타원형 (the original 320×100, id `ellipse`), 원형, 직사각형 (trapezoid, floor perspective) and 하트형; a placement's optional `variant` picks one (absent = default, so every existing rug is unchanged). **Everything that sizes/clamps/collides a piece goes through `getFurnitureSize(definition, variant)`** (`FurnitureItem`, `LiveRoomView`, `FurniturePropertiesPanel`, `furnitureObstacles`); `isValidVariant` gates `normalizePlacement`, which drops an unknown shape or one on a piece without shapes. Changing a rug's shape in the panel re-clamps it inside the room. The rug stays `collision: none` for every shape.

### Furniture shadows are drawn once, inside the SVG — never add a CSS drop-shadow on top

Every illustration draws its own two-layer shadow (`palette.ts`'s `shadowContact` — tight, directly under the actual ground-contact geometry; `shadowAmbient` — soft and wide, barely visible), positioned against that furniture's *own* computed leg-bottom/frame-bottom/pot-bottom Y, not a generic "near the bottom of the box" guess. `FurnitureItem.css` deliberately has no `filter: drop-shadow(...)` on `.furniture-item` — one used to be there, stacked on top of each SVG's own shadow, and was the actual cause of furniture looking like it floated (two uncoordinated shadows, and the CSS one wasn't aligned to any furniture's real geometry). If you add a new furniture type or touch shadow rendering, keep it SVG-internal and compute the shadow's Y from that furniture's real lowest structural element — don't reach for a CSS filter as a shortcut.

Each illustration's leg/frame/base geometry is intentionally *not* shared via a common helper across the four furniture types (sofa legs, table legs, bed frame, and plant pot all ground out differently) — but within `SofaIllustration.tsx`, note that `groundY` is the single source of truth the armrests, base frame, and legs all key off of, specifically so they can never drift apart into the kind of gap that existed before (frame ending 17% of the sofa's height above where the legs started, with nothing connecting them). When adjusting one of those three elements, adjust `groundY` rather than each element's position independently.

`FurnitureInteractionSlot` (offset + facing angle, relative to the furniture's own origin, transforming with the placement's position/scale/rotation) is now consumed — see "Furniture interaction: sitting on the sofa" below for how it resolves to a world position and seats a character. Phase 1 only ever uses a piece's *first* `kind: 'sit'` slot (one occupant per placement); the sofa's second slot, `kind: 'stand'` slots (the table's), and any interaction beyond sitting remain unused, reserved for later phases.

### `rotation` means "mirrored", not "spun"

Because the illustrations are drawn front-on, `FurniturePlacement.rotation` is typed as `0 | 180` and rendered as `scaleX(-1)` (a horizontal flip) when `180`, never an actual CSS `rotate()` — spinning a front-on sofa icon to an arbitrary angle would just look broken. The properties panel's "방향" control reflects this: it's a mirror toggle, not a rotation slider, even though the underlying field is named/typed to leave room for a future non-front-on art style.

### Window and rug are ordinary furniture, not a separate decor layer

They used to be fixed, non-draggable background elements toggled by two booleans on `homeStore` (`showWindow`/`showRug`). That's gone — `rug` and `window` are now regular `FurnitureDefinition` catalog entries (`furnitureCatalog.ts`, categories `'decor'` and `'wall'` respectively) with their own `illustrations/RugIllustration.tsx`/`WindowIllustration.tsx` and `colorways.ts` entries, placed/selected/dragged/resized/recolored/reordered/deleted through the exact same `FurnitureItem`/`FurniturePropertiesPanel`/`FurnitureCatalogPanel` code every other furniture type uses. **Don't special-case them anywhere in that pipeline** — the whole point of this shape is that `FurnitureItem` etc. never need to know a placement is a rug versus a sofa.

Two things intentionally differ from other furniture, both for a reason grounded in what these objects *are*, not in their data shape:
- `createDefaultDecorPlacements()` (`homeStore.ts`) seeds a fresh session with one `window` and one `rug` already placed, at `layer: -2`/`-1` — negative, so anything the user adds afterward (which starts at `layer: furnitureCount`, always ≥ 0) naturally sits on top without any add-flow special-casing.
- `RugIllustration.tsx` draws no displaced contact/ambient shadow pair the way elevated furniture does — a flat floor covering casting a shadow *below* itself is exactly what would make it look like it's floating instead of lying flush with the floor. Its soft edge halo matches the rug's own footprint, not a shifted-down ellipse.

**Migration**: `homeStore.ts`'s persist `merge` detects old-format saved data by the *presence* of the now-removed `showWindow`/`showRug` keys (`isLegacyFormat`) and, only for that legacy data, injects a real `window`/`rug` placement if one isn't already in the saved furniture and the corresponding flag wasn't explicitly `false`. This check matters: without gating on `isLegacyFormat`, a user who intentionally cleared their layout via "배치 초기화" (new-format data: `furniture: []`, no legacy keys) would see window/rug resurrected on every reload, since an empty array is otherwise indistinguishable from "never migrated." `RoomTheme.accent` (`roomThemes.ts`) was removed as part of this — it existed solely for the old decor components' theme-matched coloring, which rug/window's own colorways replaced.

### Wallpaper and floor are independent, freeform color+pattern settings — not fixed theme presets

The old system (5 named `RoomTheme` presets, picked via `homeStore.backgroundId`) is gone from live rendering. `homeStore.wallpaper`/`homeStore.floor` (`roomSurface.ts` types: `WallpaperSettings`/`FloorSettings`) are independently editable: a base color (16-preset picker + free `<input type="color">`, `ColorSwatchPicker.tsx`, shared by both), a pattern type, a pattern color, and a scale (floor also gets an `orientation`). `WallpaperEditor.tsx`/`FloorEditor.tsx` write straight to the store on every control — there is no separate "apply" step, and `Room.tsx` re-renders reactively.

- **Rendering**: `WallSurface.tsx`/`FloorSurface.tsx` render the wall/floor as an inline `<svg>` with a `<pattern>` def (tile content from `patterns/wallpaperPatterns.tsx`/`patterns/floorPatterns.tsx`, dispatched by pattern type) filling a `<rect className="surface-fill">`. Both use the **same `ROOM_WIDTH`/`ROOM_HEIGHT` logical-unit space furniture already uses** (`roomLayout.ts`) — this is *why* patterns never distort independently at different render sizes: everything in the room scales together via the one outer CSS `aspect-ratio` box, because tile size is defined in the same units as everything else, not raw px. `FLOOR_HEIGHT_RATIO` (`roomLayout.ts`) is the single source of truth for how much of the room's height the floor occupies — `Room.tsx` passes it to both `Room.css` (via a `--floor-height` custom property) and `FloorSurface.tsx`'s viewBox math, so they can't drift apart.
- **Pattern content is intentionally simple, stylized geometry** (a handful of primitives per pattern — stripes, a checker pair, a 5-petal flower, a star path, etc.), not photorealistic textures — matching the flat pastel-illustration style everything else in this feature uses, and fast to render as a tiled SVG pattern at any scale.
- **Schema versioning**: `homeStore.ts` now uses zustand persist's native `version`/`migrate` option (`SCHEMA_VERSION`, currently 2) instead of ad-hoc shape-sniffing — version 1 covers the earlier window/rug-as-booleans migration, version 2 covers `backgroundId` preset → independent `wallpaper`/`floor`. When the persisted shape changes again, bump `SCHEMA_VERSION` and add another `if (version < N)` branch to `migrate` rather than inventing a new detection heuristic. `roomThemes.ts` (`RoomTheme`, `getRoomTheme`) is kept **only** as the version-2 migration's color source — nothing renders with it anymore; don't reach for it for new UI.

### The furniture properties panel is the single place mutating state, not the room canvas

`FurniturePropertiesPanel.tsx` (right column) is where X/Y (number inputs), size (`scale`, bounded by that furniture's `minScale`/`maxScale`), color (`colorway` swatches), direction (mirror toggle), layer order (`bringToFront`/`sendToBack`), and delete all live, for whichever placement is `homeStore.selectedFurnitureId`. The room itself only supports click-to-select and drag-to-move. When adding a new editable property, add it here, not as inline controls on the room canvas.

### Keyboard delete is guarded against text-input focus

`DecorateScreen.tsx` has a `window` `keydown` listener for the `Delete` key that no-ops if `document.activeElement` is an `<input>`/`<textarea>`/`contenteditable` element (`isTextInputFocused()`), so typing a `-` into the X-coordinate field doesn't ever delete furniture. Any future keyboard shortcut on this screen should reuse that same guard.

### Home layout persistence, and how it stays backward-compatible

`homeStore` is wrapped in Zustand's `persist` middleware (`localStorage`, key `dearly-home`), `partialize`d to `rooms`/`activeDecorateRoomId`/`activeLiveRoomId` only — `selectedFurnitureId` is deliberately excluded (it's ephemeral UI state, not room data). `FurniturePlacement` has grown fields over time (`scale`, `colorway` were added after `x`/`y`/`rotation`/`layer`); both `addFurniture` and the persist `merge` hook run every placement through `normalizePlacement()`, which fills in sensible defaults for any field missing from older saved data. When adding a new placement field, extend `normalizePlacement` at the same time, or old saves will carry `undefined` for it forever. `homeStore` uses zustand persist's native `version`/`migrate` option (`SCHEMA_VERSION`, currently 4) for shape changes, not ad-hoc sniffing — see "Multi-room support" below for what version 3 did and how the migration chain works, and "Part colors and surface patterns" for version 4.

### Multi-room support: up to 5 independently-decorated rooms, doorway-based movement between them

The app supports 1-5 rooms per project (`roomTypes.ts`'s `MAX_ROOMS`), each independently wallpapered/floored/furnished, with characters wandering freely between them via a doorway — this replaced the earlier single-room-only version. The core, deliberately-preserved rule from the original design doc: **you only ever see characters currently in the room you're looking at** — there is no character-location tracker, no auto-follow camera, and room tabs show no character-count hints. Finding characters by clicking around the house is the point, not a gap to fill in later.

- **Data model** (`features/home/roomTypes.ts`): `Room` = `{ id, kind, name, wallpaper, floor, furniture, doorway }`. `kind` (`RoomKind`: `living`/`bedroom`/`kitchen`/`study`/`bathroom`/`hobby`/`free`) is **purely a categorization/default-bias label — it never forces specific furniture**; `name` is separately user-editable and defaults to the kind's label. `Doorway` (`{ id, roomId, entryPosition, exitPosition, passable }`) is each room's one auto-created, non-user-editable travel point — `createDefaultDoorway()` places it at the floor's bottom-center, clear of the default rug. Every room is implicitly reachable from every other one through this doorway (a "shared virtual hallway" with no literal hallway screen — there's nothing for a corridor screen to show beyond what the doorway data already captures, so one was never built). A decorative "door" furniture type doesn't exist yet in `furnitureCatalog.ts`; if one is ever added, it must stay a separate concept from `Doorway` so decorating can never sever a character's essential travel path.
- **`homeStore`'s room-scoped shape**: `HomeState.rooms: Room[]`, plus `activeDecorateRoomId` (which room `DecorateScreen.tsx`/`Room.tsx`/the editor panels currently edit) and `activeLiveRoomId` (which room `LiveRoomView.tsx` currently renders) — independent of each other on purpose, since decorating one room while "watching" a different one in Live is a normal thing to want. Every existing furniture/wallpaper/floor mutator (`addFurniture`, `moveFurniture`, `setWallpaper`, etc.) kept its **exact original signature** and now just resolves "which room" internally via `activeDecorateRoomId` — this is what let every decorate-phase component (`Room.tsx`, `FurnitureCatalogPanel.tsx`, `FurniturePropertiesPanel.tsx`, `WallpaperEditor.tsx`, `FloorEditor.tsx`, `DecorateToolbar.tsx`, `DecorateStatusBar.tsx`) get room-awareness by swapping only their **read-side** selector (`state.furniture` → `getActiveDecorateRoom(state).furniture`, etc.) without touching a single action call site or duplicating any editor component per room. `getActiveDecorateRoom(state)`/`getActiveLiveRoom(state)` (exported from `homeStore.ts`) are the two selector helpers every room-aware read goes through; both fall back to `rooms[0]` defensively if the active id somehow doesn't match any room. New room actions: `addRoom(kind, name, preset)` (refuses past `MAX_ROOMS`, returning `''`), `renameRoom(id, name)`, `removeRoom(id)` (refuses — no-ops — if `id` is the last room; reassigns `activeDecorateRoomId`/`activeLiveRoomId`/`selectedFurnitureId` back to the remaining first room if they pointed at the deleted one), `setActiveDecorateRoom(id)`, `setActiveLiveRoom(id)`.
- **Migration to v3** (`homeStore.ts`'s `migrate`): version 3 is the single-flat-room → `rooms` array change. Regardless of the persisted data's starting version (0, 1, or 2), the migration chain always funnels through the `version < 3` branch last and returns the new `{ rooms: [room], activeDecorateRoomId: room.id, activeLiveRoomId: room.id }` shape — so `merge` (which runs on `migrate`'s *output*, not the raw persisted data) only ever has to handle the current `rooms`-array shape, never the old flat one. The existing single room's furniture/wallpaper/floor become that one room's data verbatim — nothing about a pre-existing layout changes, only its address (a room id) does. `merge` additionally falls back to `rooms[0]` if a persisted `activeDecorateRoomId`/`activeLiveRoomId` doesn't match any room in the persisted `rooms` (e.g. it pointed at a room that was later deleted in a save written by a build with a bug, or any other inconsistency) — never crashes on a dangling id.
- **`RoomTabs.tsx`** (`features/home/`) is the one shared room-selection UI mounted in both `DecorateScreen.tsx` (wired to `activeDecorateRoomId`/`setActiveDecorateRoom`) and `LiveScreen.tsx` (wired to `activeLiveRoomId`/`setActiveLiveRoom`) — a room tab list, double-click-to-rename, a "+ 방 추가" form (kind + name + preset picker, disabled with an explanatory `title` at `MAX_ROOMS`), and delete (only shown when 2+ rooms exist; always confirms; if the room being deleted currently has any characters in it — read from `characterMovementStore`, filtered by `roomId` — the confirm UI requires picking a target room via a `<select>` with no default selection before the delete button enables, then calls `characterMovementStore`'s `moveCharacterToRoom` for each occupant, teleporting them to the target room's own doorway `entryPosition`, before actually calling `removeRoom`). Deleting a room never touches any other room's data — `removeRoom` only filters the one entry out of `rooms` and, only if needed, repoints the two active-room ids.
- **Character room state** (`characterMovementStore.ts`): each entry now also carries `roomId` (which room this character physically occupies right now — the single source of truth both `LiveRoomView.tsx`'s visibility filter and the movement tick's per-room grouping key off of) and `destinationRoomId` (non-null only while a character is walking toward its *current* room's doorway to leave — see the transition flow below; cleared, not preserved, if a mid-path collision forces a replan, so an abandoned room-change attempt never leaves stale intent to silently resume later) and `currentBehavior` (`BehaviorType | null`, the behavior currently driving `destination`). `syncCharacterIds`'s `spawn` callback now returns `{ position, roomId }` instead of a bare point — new characters spawn into whichever room is currently `activeLiveRoomId`.
- **`changeRoom` as a 5th movement behavior** (`character/personalityTags.ts`'s `BehaviorType`, `movementEngine.ts`'s `pickBehavior`): alongside `wander`/`rest`/`approach`/`seekSolitude`, a character can now roll `changeRoom` — gated to weight 0 (never picked) via `pickBehavior`'s `canChangeRoom` param whenever `rooms.length <= 1`, and given a lower shared base weight (0.35 vs. 1 for the other four, `movementEngine.ts`'s `BEHAVIOR_BASE_WEIGHT`) so characters don't restlessly bounce rooms every time they pick a new destination. 호기심/활발함 add a small positive `changeRoom` delta (curious/energetic characters go looking through the house more), 내향적/게으름 a small negative one — summed with the shared per-tag `OVERRIDES` table the other behaviors already use.
- **Room-choice time-of-day bias** (`movementEngine.ts`'s `roomKindBiasForHour`/`pickDestinationRoomId`): when `changeRoom` is picked, the destination room is chosen with a weighted roll across every *other* room, biased toward a `bedroom`-kind room at night (21:00-05:00) and a `kitchen`-kind room at the three real-clock mealtime windows — the same "real-clock-hour, not a fake in-game clock" honest-simplification pattern `autoDialogueEngine.ts`'s `isTimeOfDayEligible` already established for `morning-greeting`/`bedtime` lines. This is a disclosed simplification of the spec's "이용 가능한 가구" (furniture-availability-aware) room-choice request — there's no tracked notion of "what a room offers" beyond its `kind` label, so that part of the request isn't implemented, only the honestly-buildable hour-based bias is.
- **Doorway-transition state machine** (`useCharacterMovementSimulation.ts`) — a character never teleports room-center to room-center. On rolling `changeRoom`, its `destination` is set to its *current* room's own `doorway.exitPosition` and `destinationRoomId` to the chosen target room; it then walks there exactly like any other destination. Only once it actually arrives at that point (checked before any new-destination logic each tick, so an arrival mid-transition is never mistaken for an ordinary "picked a new one" moment) does `completeRoomChange()` fire: `roomId` switches to the target room, position teleports to *that* room's own `doorway.entryPosition`, and `destination`/`destinationRoomId`/`currentBehavior` all clear — so the very next tick picks a fresh, ordinary in-room destination. A mid-path collision replan during a transition (`wouldCollide`) clears `destinationRoomId` too, abandoning the attempt cleanly rather than leaving it to silently resume from a stale, no-longer-relevant state.
- **Doorway-stacking deadlock, and the two-part fix** (`movementEngine.ts`'s `pickDoorwayArrivalPosition` + `movementConfig.ts`'s `MAX_STUCK_TICKS`): because `createDefaultDoorway` gives every room the exact same fixed coordinate, two characters can genuinely end up standing on the identical point — one already idling at a doorway, another arriving there via `completeRoomChange`. This used to permanently freeze the arriving character: `CHARACTER_RADIUS * 2` (40 units, the minimum separation collision enforces) is larger than `MOVE_SPEED_PER_TICK` (14 units), so *any* reachable point within one tick's move distance from a shared starting point is still inside the other character's collision radius — the retry-based "pick a new random destination" loop could never succeed, no matter how many times it retried. Root-cause mitigation: `completeRoomChange` now calls `pickDoorwayArrivalPosition`, which checks whether the doorway point is currently occupied (by furniture or another character already in the target room) and, if so, jitters the landing point a short distance away (still "at the doorway" in spirit, within `DOORWAY_ARRIVAL_JITTER_RADIUS`) before accepting it — this is what stops the stacking scenario from happening in the first place, in the common case. Defense in depth: every character now tracks `stuckTicks` (`characterMovementStore.ts`) — consecutive ticks its step has been blocked by collision, reset to 0 on any successful step — and once that hits `MAX_STUCK_TICKS` (6), the blocked step is forced through anyway rather than replanned again, guaranteeing no permanent deadlock even in whatever scenario the de-stacking jitter doesn't cover (e.g. furniture genuinely boxing in the only doorway-adjacent floor space). A brief one-tick visual overlap is judged far better than a character frozen forever. This was found and fixed as a real bug (not a hypothetical) — see `useCharacterMovementSimulation.test.tsx`'s "multi-room" describe block, scenario 9 in particular, which reproduces the stacking scenario directly.
- **A conversation interrupting a mid-room-change character must clear its room-change intent too** (`autoDialogueTrigger.ts`'s `runConversation`): if an encounter conversation starts while a character is walking toward a doorway (`destinationRoomId` set), the conversation's `finally` block now clears `destinationRoomId`/`currentBehavior` for both participants, not just `destination`/`status` as before. Without this, a character interrupted mid-transition would resume wandering normally afterward, but the *next* ordinary destination it happened to reach (anywhere in the room, unrelated to the doorway) would satisfy the stale `destinationRoomId && destination && hasArrived(...)` check and trigger a "phantom" room switch — teleporting the character into a room it never actually walked to. Both participants are reset uniformly in that `finally`, regardless of which one (if either) was actually mid-transition.
- **One shared tick loop, not one per room** (`useCharacterMovementSimulation.ts`): there is still exactly one `setInterval`, mounted once from `LiveScreen.tsx` — every room's characters are processed in the same tick, not via per-room intervals. Each tick, obstacles (`furnitureObstacles`) are computed once per room (`obstaclesByRoom`, keyed by room id, sourced from *that room's own* furniture, never the observed room's) and every character reads its own room's obstacle set via its own `roomId` — this is what makes simulation for rooms the user isn't currently looking at keep running exactly as before (§7's "다른 방의 생활도 계속 진행되어야 한다"), with no separate loop and no separate code path.
- **Per-room encounter detection**: `otherPositions` for movement/collision purposes is filtered to same-`roomId` characters only (so a character in the kitchen never "collides" with one in the bedroom just because both rooms reuse the same logical `ROOM_WIDTH`×`ROOM_HEIGHT` coordinate space). Likewise, `detectEncounters()` is called once per room-group (characters bucketed by their current `roomId` after that tick's movement), and the resulting `newlyEncountered`/`currentlyNear` are merged across rooms into one combined near-set for the next tick — two characters can never be flagged as "encountered" unless they're actually standing in the same room. `autoDialogueTrigger.ts`/`autoDialogueEngine.ts` needed **no changes at all** for this — they already operate on whichever pair of ids they're given, with no assumption about location, so room-scoping the *detection* step alone was sufficient.
- **Only the observed room renders** (`LiveRoomView.tsx`, the concrete mechanism behind spec §6): furniture/wallpaper/floor come from `getActiveLiveRoom(state)`, and rendered characters are filtered to `characterMovementStore.byId[c.id]?.roomId === activeLiveRoomId` — a character who has moved to another room simply stops appearing here, with no special-casing needed elsewhere. There is deliberately no character-location list, no room-tab highlighting for "a character is here," and no auto-follow camera anywhere in this feature — `RoomTabs.tsx` renders only room names, never counts or hints.
- **Manual "대화하기" is scoped to the observed room** (`LiveScreen.tsx`, spec §9): the pair-candidate pool (`roomPairs`/`availablePairs`) is built only from characters whose `characterMovementStore` entry currently has `roomId === activeLiveRoomId` — a registered, free character standing in a different room is never offerable, and the button's disabled-reason text reflects this ("이 방에서 지금 대화할 수 있는 캐릭터가 2명 미만이에요"). The **relationship-type picker stays global** (built from every registered character, unfiltered by room) since a relationship type is a property of the pair itself, not of where they currently happen to be standing.
- **Not built**: real proximity-aware furniture availability driving room choice (see above — only the hour-based bias exists), a literal corridor/hallway screen (rooms are connected through doorway data only, per the spec's own "초기 버전은 실제 복도 화면 없이 가상 연결로 처리해도 됨" allowance), and decorative door furniture (doesn't exist yet — see the data-model bullet above for what must stay true if it's ever added).

### There is no AI/API integration anywhere in this project — everything is local

An earlier version of this project called the Anthropic API directly from the browser (`features/ai/`: an `aiConfigStore`, provider adapters, a prompt builder, a response validator, an "AI 연결" tab) to generate dialogue on demand. **That entire system was removed** — not hidden, not stubbed, the whole `features/ai/` directory and the `AIConnectionScreen`/`'ai'` app phase are deleted — in favor of the fully local, no-network auto-dialogue engine described below. A few things follow from this that are easy to get wrong if you don't know the history:

- There is no API key anywhere in this app, session-memory or otherwise. Nothing here should ever add a network call, a provider adapter, or a "connect" UI back in without the user explicitly asking for it again.
- `CharacterAIProfile` (in `features/character/types.ts`) and `CharacterAIProfileEditor.tsx` **keep their "AI" naming on purpose**, even though nothing here talks to an AI anymore — `aiProfile` is a persisted JSON field name (`characterStore`'s `dearly-characters` key), and renaming it would need a migration for zero functional benefit. Read "AI profile" as "character persona/tone profile" — tone, dialogue-line library, personality tags — not as anything related to an external model.
- There was never anything to clean out of `localStorage` for this removal: `aiConfigStore.ts` was deliberately a plain `create()` with no `persist` middleware (the API key was meant to vanish on refresh even before this removal), so no persisted API config or key ever existed to migrate away from. `characterStore`/`homeStore`/`dialogueFrequencyStore`/`relationshipStore` (all real save data) are untouched by this change.

### Character tone settings and the dialogue-line library

`CharacterAIProfileEditor.tsx` is a two-tab UI: **말투 및 대사** (tone + dialogue lines, described below) and **기타 설정** (the simpler personality/habits/preferredActivities/relationship/neverChange free-text fields from the original AI profile).

- `CharacterToneSettings` (`character/types.ts`) has a `baseTone` select (존댓말/반말/혼합/직접설정) that exists purely as a data-entry shortcut — `toneDetail` (free text) is what's actually authoritative and sent to the AI. Never make any UI or prompt logic treat `baseTone` as overriding `toneDetail`; the spec is explicit that free input always wins.
- `CharacterDialogueLine` is one example line: `categoryId` (references either a built-in `SituationCategory` from `features/dialogue/situationCategories.ts`, or one the user added via `situationCategoryStore.ts`), a free-text `situationNote` (the line's own human-readable label — distinct from `categoryId`, which is the machine-matchable bucket), `text`, `emotion`, `tags`, and `isFallback`. Situation categories are **shared across every registered character** (a situation like "아침" isn't character-specific), so they live in their own store, not nested in `characterStore`.
- `isFallback` is now consumed by `features/dialogue/autoDialogueEngine.ts`: if every non-recently-used candidate for a speaker's turn is excluded, the engine retries with only `isFallback`-marked lines (recency-exempt, every other guard still applies) before giving up and skipping the conversation. It never invents a line outside what's registered.
- `personalityTags` (`character/types.ts`, up to `MAX_PERSONALITY_TAGS` = 5, ids from the 71-tag list in `character/personalityTags.ts`) plus `customPersonalityTags` (user-typed personalities not in that list, per character) are edited via `PersonalityPicker.tsx` — search + category filter + selected-tag pills + a 0/5 counter + custom-tag entry, all in one shared, controlled component. **It's rendered in two places, not duplicated**: `CharacterForm.tsx` (new-character registration, operating on local `useState` before the character has an id) and `CharacterAIProfileEditor.tsx`'s 기타 설정 tab (editing an already-registered character, operating on that character's `aiProfile` directly via `updateAIProfile`). Both feed the exact same weighting in `autoDialogueEngine.ts`/`useCharacterMovementSimulation.ts`; it is never sent to any AI prompt (there is none — see "There is no AI/API integration" above).
- **A custom tag never gets an invented effect.** `resolveWeightingTagIds()` (`personalityTags.ts`) is the one place raw `personalityTags` (a mix of built-in and custom ids) get translated into the subset of built-in ids that actually drive weighting: a built-in id passes through as-is, a custom tag contributes nothing *unless* the user explicitly picked a built-in tag to "act like" (`CustomPersonalityTag.mappedTagId`) when creating it, in which case it borrows that tag's full weighting. Every caller of the weighting functions (`initiateWeightFor`, `startChanceWeightFor`, `behaviorWeightFor`, `lineAffinityWeightFor`) must run raw ids through this resolver first — they don't do it themselves.
- The registration screen's old free-text "성격" input is gone — `CharacterTraits.personality: string` still exists in the data model (untouched, never deleted) purely as the landing spot for **pre-tag-system saved data**; see `characterStore`'s migration note below for how an old string value becomes a tag or custom tag exactly once. `CharacterList.tsx`'s summary line now shows resolved tag labels (`getPersonalityLabel`) when any exist, falling back to the raw `traits.personality` string only for the (now theoretical) case a character has neither.
- `dialogueLines`, like `FurniturePlacement`, is never touched by "tone normalization" — whatever text the user types is stored verbatim.
- `CharacterDialoguePreview.tsx` reuses `dialogue/DialogueBubble.tsx` — the same presentational component `DialogueFeed.tsx` (the live simulation) renders — so a preview in the setup screen always looks exactly like the real thing. If you change bubble styling, it changes in both places automatically; don't fork a second bubble component for previews.
- Dialogue *exchange* bundles, situation-trigger → line-selection playback, recent-line-repeat avoidance, and configurable output frequency are now built — see "Auto-dialogue engine" below. This registered-line library is the *only* source of dialogue text anywhere in the app now — there is no AI-generation path left to fall back to or compare against.

### `characterStore` persistence and its migration

`characterStore` is now `persist`-wrapped (`localStorage`, key `dearly-characters`) — it started this project unpersisted, so `normalizeCharacter()` (in `characterStore.ts`) has to handle both "fields added after persistence started" (the usual case, same pattern as `homeStore`'s `normalizePlacement`) *and* real shape changes: a saved character whose `aiProfile.tone` is a plain string (the pre-tone-system shape) gets it converted into a `CharacterToneSettings` object (`baseTone: 'custom'`, `toneDetail` = the old string), and a non-empty old `sampleLines` string becomes one migrated `CharacterDialogueLine`. No user-entered text is dropped by this — only reshaped. Extend `normalizeCharacter` (not just the type) whenever `CharacterAIProfile`'s shape changes again.

**Legacy `traits.personality` string → tags, exactly once.** The gate is field *presence*, not emptiness: if `aiProfile.personalityTags` is missing from the raw data entirely (pre-tag-system save), `migrateLegacyPersonalityString()` runs once — an exact label match against a built-in tag becomes that tag id, anything else becomes one preserved `CustomPersonalityTag`, and the original `traits.personality` string is left untouched either way (never cleared). If `personalityTags` is already present as a real array — even `[]`, meaning the user deliberately cleared their selection after a prior migration — it's used as-is and the string is never consulted again. This mirrors the exact "detect by field absence, not emptiness" pattern `homeStore.ts`'s window/rug migration already established, for the same reason: without it, a deliberately-emptied selection would look identical to "never migrated" and get silently resurrected on the next reload.

There is still no project-level JSON export/import feature in this app (despite being mentioned as a future compatibility requirement) — don't assume one exists when reasoning about "what gets saved."

### `dialogueStore.ts` and `DialogueFeed.tsx`: manual and automatic dialogue share one engine, one output path

There used to be a manual "대화하기" button that called the Anthropic API on demand — that whole stack (`features/ai/`) is deleted and never coming back. The button itself **is back**, but it now calls `autoDialogueTrigger.ts`'s `startManualConversation()` — the exact same local `CharacterDialogueLine`-based engine the encounter-triggered path uses, just entered a different way (see "Auto-dialogue engine" below for the shared `runConversation()` core). No network call, no API key, ever.

- `features/dialogue/dialogueStore.ts` holds the append-only conversation history (`appendLines` — never replaces `entries`), the conversation-tracking runtime state (`activeConversations`/`isCharacterBusy`/`startConversation`/`endConversation`/`lastConversationEndAtByPair`/`recentAutoLineIdsByCharacter`), and `activeBubbleByCharacter` (a character id → their current line, for the floating speech bubble in `CharacterToken.tsx` — set when their line is appended, cleared for both participants only when the whole conversation ends, not on a per-line timer). None of this is persisted (unlike `homeStore`) — it's ephemeral session state, not save data.
- `LiveScreen.tsx`'s "대화하기" button (`autoDialogueConfig`'s frequency panel, bottom of it) calls `startManualConversation(idA, idB, situationRef, mountedRef)`. Candidates are scoped to the currently-observed room (`roomPairs`, see "Multi-room support" below) — with exactly 2 available characters in that room they're auto-selected (mirroring the relationship pair-picker's own "only show a picker when there's a real choice" rule); with 3+ it shows a dedicated pair-`<select>` — a *different* one from the relationship pair-picker, deliberately: which pair currently talks and which pair's relationship you're editing are unrelated choices, and conflating their state would let picking one accidentally change the other. That picker is built from `roomPairs` filtered by `!dialogueStore.isCharacterBusy(id)` for both sides, so a character already mid-conversation (auto or manual) can never be selected into a second one — this is the same guard `startConversation` already enforces, just also reflected in what the UI even offers. The button is disabled while paused (an explicit, disclosed rule — a click while paused would otherwise start a conversation whose bubbles simply never reveal, which is worse than not offering it) or while fewer than 2 characters are available *in the observed room*, and shows *why* via its `title`. **Manual generation works in every frequency mode, including 'quiet'** — `startManualConversation` never calls `rollShouldStartConversation` at all, since 'quiet' is specifically "no *automatic* dialogue," never a block on the manual button.
- `LiveScreen.tsx`/`DialogueFeed.tsx` only render `dialogueStore` state — no fetch, no prompt text, no schema logic in the component tree. `DialogueFeed.tsx` picks a bubble's left/right side by the speaking character's index in `characterStore.characters` (even/odd), not by "is this the other character" — with up to 5 characters there's no single "other side" anymore, so this is the simplest scheme that still visually distinguishes speakers (the bubble's name/avatar is what actually identifies who's speaking).
- Not built: a persisted dialogue history (entries reset on reload), cost/token tracking (moot — there's no API to meter).

### Character movement, collision, and encounter detection

Up to 5 characters (`CharacterForm.tsx`'s `MAX_CHARACTERS`) now wander the decorated room in real time and trigger auto-dialogue when they actually get close to each other — this replaced an earlier, disclosed-as-a-simplification version that had no movement system at all and rolled dialogue on a flat 15-second timer instead. That earlier version is gone; this is the real thing, at the fidelity described below.

- **`features/simulation/movementConfig.ts`** — the one place movement's numeric constants live (`MOVEMENT_TICK_MS`, `MOVE_SPEED_PER_TICK`, `CHARACTER_RADIUS`, `ENCOUNTER_DISTANCE`, `MAX_DESTINATION_ATTEMPTS`, `FLOOR_TOP_Y`). There's still no in-game time multiplier or a pre-existing movement-speed constant anywhere to match against (checked again before choosing these), so `MOVE_SPEED_PER_TICK` is a plain logical-units-per-tick value chosen so crossing the room takes roughly 10-13 real seconds.
- **`features/simulation/movementEngine.ts`** — pure, tested functions: `furnitureObstacles()` turns `homeStore.furniture` into collision rects (centered on each placement, sized by its `FurnitureDefinition` × `scale`; `rug` is excluded — it's a floor covering, not an obstacle, matching how it's already excluded from shadow-casting), `circleIntersectsRect`/`circlesOverlap` are the actual collision math, `pickRandomDestination` finds a free point on the walkable floor band (`FLOOR_TOP_Y` down to `ROOM_HEIGHT`, both inset by `CHARACTER_RADIUS`) via bounded retry, and `stepToward`/`hasArrived` move a point without overshooting. **Collision avoidance is retry-based, not real pathfinding**: a character blocked mid-path by furniture or another character just picks a brand-new random destination next tick instead of routing around the obstacle. This is disclosed as a deliberate simplification, not a hidden limitation — if smoother routing is ever wanted, `useCharacterMovementSimulation.ts`'s per-tick collision branch is the only place that needs to change.
- **`features/simulation/encounterEngine.ts`** — `detectEncounters()` is pure and rising-edge-only: given current positions and the set of pairs that were near on the *previous* call, it returns only pairs that just crossed into `ENCOUNTER_DISTANCE` this call, plus the updated near-set to pass in next time. This is what stops two characters who are simply standing next to each other from re-triggering a dialogue attempt every tick — the encounter fires exactly once per approach, and again only after they've separated and come back.
- **`features/simulation/characterMovementStore.ts`** — not persisted (ephemeral runtime state, same rationale as `dialogueStore`'s conversation-tracking fields). `syncCharacterIds(ids, spawn)` is called every tick and is what keeps this store in sync with `characterStore.characters` as characters are added/removed mid-session — a removed character's movement entry is dropped automatically within one tick, with no explicit cleanup code needed anywhere else. `status` is `'idle' | 'moving' | 'talking' | 'seated' | 'lying' | 'lingering'`; a character's movement pauses (no destination changes, no stepping) for exactly as long as `status` is any of the last four — see "Furniture interaction" below for those. Each entry also carries a `roomId` (and `destinationRoomId`/`currentBehavior`) now that rooms are multi — see "Multi-room support" below for the doorway-transition flow this drives.
- **Personality-weighted behavior selection** (`movementEngine.ts`'s `pickBehavior`, `pickApproachDestination`, `pickSeekSolitudeDestination`): whenever a character needs a new destination, it first rolls one of 4 real in-room behaviors — `wander` (plain random point, the only behavior that existed before this), `rest` (stand still for `REST_TICKS`, tracked in `characterMovementStore`'s `restTicksRemaining`), `approach` (aim near a random other character, biasing toward encounters), `seekSolitude` (aim for the point farthest from everyone else) — weighted by `behaviorWeightFor()` for the character's resolved tags. 활발함/호기심 raise `wander`, 차분함/게으름 raise `rest`, 사교적 raises `approach`, 내향적 raises `seekSolitude`. A 5th behavior, `changeRoom` (moving to a different room entirely), exists alongside these when more than one room does — see "Multi-room support" below. **Honestly out of scope**: 부지런함's requested "정리·청소" (cleaning) behavior has no real implementation — there's no furniture-interaction system to attach it to (`FurnitureInteractionSlot` is still inert data, see the furniture section above) — so 부지런함 stays a neutral tag rather than faking an effect.
- **`features/simulation/useCharacterMovementSimulation.ts`** — the tick loop (`setInterval` at `MOVEMENT_TICK_MS`, mounted once from `LiveScreen.tsx`, reading everything live via `.getState()` rather than closed-over props/state, to avoid acting on stale values). Each tick: sync character ids → move every non-`'talking'` character one step (picking a new destination on arrival or on a blocked step) → detect encounters from the *updated* positions → for each newly-encountered pair, fire-and-forget `autoDialogueTrigger.ts`'s `attemptEncounterConversation()`. Does nothing at all while `simulationStore.isRunning` is false.
- **`features/simulation/LiveRoomView.tsx` + `CharacterToken.tsx`** — a read-only rendering of the decorated room (same `WallSurface`/`FloorSurface`/`FurnitureIcon` pieces `Room.tsx` uses, minus drag/select — furniture here is fixed dressing, not editable) with each character rendered as a full sprite on top. Mounted directly in `LiveScreen.tsx` above the existing situation/dialogue panels.
- **Character sprite rendering** (`CharacterToken.tsx` + `characterRenderConfig.ts` + `character/characterDisplay.ts`): the uploaded `imageDataUrl` renders as a plain `<img>` at `height: N%; width: auto` — no `object-fit: cover`, no `border-radius`, no crop — so transparent PNGs and non-square art render at their real aspect ratio, never circle-masked. `BASE_CHARACTER_HEIGHT` (`characterRenderConfig.ts`) is **120 room-logical units, not raw CSS px** — like every other room dimension (`roomLayout.ts`), a literal pixel value would only look right at one specific viewport width, since the room scales via `aspect-ratio`, not a fixed size; 120 units is comparable to the bed's 144-unit height, i.e. genuinely large. Each character has its own `displayScale` (`Character.displayScale`, 0.5-2, default 1, set via a slider in `CharacterAIProfileEditor.tsx`'s 기타 설정 tab, persisted through the normal `characterStore` save path — no separate "size" store). **This is a purely visual multiplier and never touches `CHARACTER_RADIUS`/collision math** — a giant sprite and a tiny one collide identically, by design (§4 of the spec that requested this explicitly asked for that separation).
  - **Foot-anchored positioning, not center-anchored**: `characterMovementStore`'s `x`/`y` (already the collision circle's center) is treated as the character's *foot* point. The wrapper `<div>` sits at that exact point with no transform of its own; every visual child (shadow, sprite, name, speech bubble) is positioned at the wrapper's own origin `(0,0)` and offsets itself independently — the shadow centers there (`translate(-50%,-50%)`), the sprite's *bottom* sits there (`translate(-50%,-100%)`), the name sits just below it, the bubble sits just above the sprite's own top edge. Because all of them share one positioned ancestor and the same tick-driven `left`/`top`, they can never visually separate while moving. **CSS gotcha worth knowing if you touch this file**: `.character-token` itself is given `width:100%; height:100%` even though it paints nothing — a percentage `height` on an absolutely-positioned child only resolves against a containing block with a *definite* size, and without this the wrapper's own size would be "auto" (determined by its content, i.e. circular), silently making the children's percentage heights compute as unset.
  - **Alpha-channel bounding-box detection auto-corrects foot alignment and real size** (`character/characterImageAnalysis.ts` + `character/characterDisplay.ts`'s `computeCharacterDisplayGeometry`) — this replaced an earlier version where `footOffsetRatio` was the *only* correction, which couldn't account for a small character drawn in the middle of a much larger canvas (the sprite would render at the full canvas's height, making the character itself tiny). Now: on registration (`CharacterForm.tsx`'s `handleImageChange`), the uploaded PNG is decoded into an offscreen `<canvas>` and scanned for its opaque-pixel bounding box (`analyzeCharacterImageBounds`, alpha > `ALPHA_THRESHOLD` = 24/255, filtering out anti-aliased fringe pixels) — this runs **in the background, never blocking the preview or the submit button**; if it hasn't finished (or fails — no real canvas pixel backend, a corrupt file, decode error) by submit time, the character is created with `imageBounds: null`, which every consumer treats as "no correction available," i.e. exactly the pre-analysis behavior. The result (`Character.imageBounds`, four 0-1 ratios: `topRatio`/`bottomRatio`/`leftRatio`/`rightRatio`) is computed **once at registration**, not re-analyzed on every render, and stored alongside the character (normalized/validated on load by `characterStore.ts`'s `normalizeImageBounds`, falling back to `null` for any malformed persisted value).
    - **Real-size correction**: `computeCharacterDisplayGeometry` scales the *whole* uploaded image (not just the visible character) up by `1 / (bottomRatio - topRatio)` before applying `BASE_CHARACTER_HEIGHT`, so the character's own opaque region — not the full transparent-padded canvas — ends up roughly `BASE_CHARACTER_HEIGHT * displayScale` tall on screen, regardless of how much empty margin the source PNG has.
    - **Foot alignment**: the same function adds an automatic offset (`renderedImageHeightUnits * (1 - bottomRatio)`) to push the sprite down exactly enough to compensate for any transparent padding *below* the detected feet, so the real foot pixels — not the image file's own bottom edge — land on the movement/ground point. `footOffsetRatio` (`Character.footOffsetRatio`, -0.3 to 0.3, still a slider in `CharacterAIProfileEditor.tsx`) **now combines additively on top of this automatic correction** — it was not duplicated or replaced, per the explicit instruction to integrate rather than re-implement; a user's own manual correction is never silently overwritten by the automatic one. Both are expressed as a fraction of the sprite's own *current* rendered height (`renderedImageHeightUnits`, not the old flat `BASE_CHARACTER_HEIGHT * displayScale`), so they keep working correctly as `displayScale` changes and the ground point never moves.
    - **Shadow sizing deliberately does NOT use the bbox-corrected height** — it stays keyed to `BASE_CHARACTER_HEIGHT * displayScale` alone (the character's *intended* body size), specifically so a PNG with lots of transparent padding doesn't grow an oversized shadow just because of empty pixels around a small drawing. The shadow's own position was already ground-anchored unconditionally before this feature and remains so — it never received either correction, old or new.
    - **The speech bubble now anchors to the real drawn character's top edge** (`bubbleOffsetUnits`), not the image file's own top edge, which — for a heavily-padded PNG — could be far above the character's actual head.
    - **Not unit-tested directly**: `analyzeCharacterImageBounds` itself (the `<canvas>`/`Image`-decoding glue) has no real pixel backend to exercise in jsdom, so it's excluded from direct test coverage by design — `computeOpaqueBounds` (the pure pixel-scanning core it delegates to) carries the actual scanning-logic test coverage (`characterImageAnalysis.test.ts`), and `computeCharacterDisplayGeometry` (the pure geometry math) is fully covered in `characterDisplay.test.ts`, both against synthetic inputs rather than a real decoded image.
  - **Front/back order**: `zIndex: Math.round(movement.y)` on the wrapper, so a character lower in the room (larger y) renders in front of one higher up — this only orders characters relative to each other, as requested; it does not attempt correct depth occlusion against furniture (furniture's `layer` values are small integers in a completely different range, and characters already rendered above all furniture by DOM order before this change too — not a regression, just never attempted).
  - **Load-failure fallback**: an `onError` handler swaps the `<img>` for a small placeholder (the character's first initial) — this is the *only* case a placeholder shows; a registered character always has `imageDataUrl` since registration requires one.
  - **Floating speech bubble**: `CharacterToken` reads `dialogueStore.activeBubbleByCharacter[character.id]` and renders it right above the sprite when present — correct per-character attribution is automatic (it's a plain id-keyed lookup, same as everything else here), and it works identically regardless of how many concurrent conversations exist. It shows a participant's *current* line for the conversation's whole duration (not a per-line fade) and both participants' bubbles clear together the moment their conversation ends — see `autoDialogueTrigger.ts`'s `runConversation()`.
- **Not built**: real pathfinding around obstacles (see above), a "natural" idle-pause between destinations (characters currently wander continuously, immediately picking a new destination on arrival), and per-character walk-cycle animation (tokens just move; the CSS `transition` on position is what makes it look smooth rather than teleporting between ticks).

### Furniture interaction: sitting on the sofa and on ordinary chairs (phase 2 — independent multi-seat, manual only)

Characters can be sent to actually use a piece of furniture, not just walk around it. Phase 2 extends phase 1's single-occupant-only design to **independent per-seat** reservation/occupancy, and connects it to the catalog's two ordinary chairs. Still manually triggered only — the bed/table and any automatic ("characters sit down on their own when idle") use remain future phases, not attempted here.

- **Which pieces actually got seats, and why** (checked against the real catalog/illustration geometry, not assigned blanket-style): `sofa` (id `sofa`, the original 224-wide entry) is the one genuine 2-seat sofa — its two `interactionSlots` (`sofa-left`/`sofa-right`) already existed, unchanged, derived from `SofaIllustration`'s real cushion centers. `dining-chair` and `office-chair` each gained exactly **one** `kind: 'sit'` slot (id `seat`), with `offsetX: 0` (both chairs draw their seat cushion horizontally centered) and `offsetY` read directly off their own illustration's seat-cushion block — `DiningChairIllustration`'s seat spans y=[0.42h,0.55h] (center 0.485h → offset −0.015h = **−1.4** at h=96); `OfficeChairIllustration`'s spans y=[0.5h,0.62h] (center 0.56h → offset +0.06h = **+6.7** at h=112) — never guessed. `sofa-single` (1 cushion), `sofa-long` (a genuine **3**-cushion sofa by its own `SofaBody` geometry — `cushions: 3` — discovered while checking real sizes, but out of scope: this batch named only "2인용 소파"), and `armchair` deliberately keep empty `interactionSlots`, same as every other non-seat furniture type — not sittable yet, left for the user to request explicitly rather than assumed in scope.
- **Geometry** (`features/simulation/furnitureInteractionEngine.ts`, pure, tested): `getSitSlots(definition)` returns *every* `kind: 'sit'` slot a definition declares, in catalog order — two for the sofa, one for a chair; `getPrimarySitSlot` (still used wherever "does this piece have any seat at all" is the only question, e.g. `isSittableFurniture`) is just `getSitSlots(definition)[0]`. `resolveSeatPosition`/`resolveSeatFacing`/`resolveApproachPoint` are unchanged from phase 1 — they already took a specific `slot`, so extending to multiple slots per placement needed no changes to the geometry math itself, only to which slot gets passed in.
- **Reservation state is keyed per *seat*, not per placement** (`features/simulation/furnitureUsageStore.ts`, rewritten from phase 1's per-placement `byPlacementId` to `bySeatKey`, keyed by an opaque `placementId:slotId` string) — ephemeral, **not persisted**, same rationale as before: a seat reservation or in-progress approach is exactly as reproducible on reload as any other in-progress movement, and none of it is real save data. `reserve` refuses if that *exact* seat is already taken, or if the character is already using a *different* seat — so the sofa's two seats are now fully independent (one filling up never blocks or touches the other), while "one seat per character" still holds. `release`/`releaseSeat` only ever touch one seat's own entry; `releasePlacement` is the one operation that sweeps *every* seat belonging to a placement at once (whole-furniture deletion/move/rotate/resize) — tested explicitly (`furnitureUsageStore.test.ts`) to prove releasing one seat never touches a seatmate's.
- **Orchestration** (`features/simulation/furnitureUsageTrigger.ts`) — same shared functions for both the sofa and every chair (per the spec's "공통 좌석 정의와 공통 상태 전환 로직을 재사용", not a copy-pasted chair engine):
  - `startSitting(characterId, placementId, slotId?)` — `slotId` is optional: omitted, it auto-picks the first currently-free seat (the only real choice for a one-seat chair, and exactly what every phase-1 call site — including the regression tests — already relied on for the sofa); given, it targets that exact seat. Validates same-room, then busy/talking, then resolves and reserves the target seat (`'occupied'` if that seat — or, with no `slotId`, every seat on the piece — is already taken). **Seat reassignment**: if the character is already on a *different* seat, that seat is released (bookkeeping only, no walk back to it) before the new one is reserved, per the spec's "기존 좌석을 안전하게 해제한 뒤 새 좌석을 예약" — targeting the exact seat they're already on/walking to is a harmless no-op.
  - `standUp(characterId)` — unchanged in shape from phase 1, and still only ever touches that one character's own seat (never a seatmate's, since release is already seat-scoped).
  - `releaseFurnitureUsage(characterId)` — unchanged.
  - `evictPlacementUsage(placementId)` — now ends **every** occupant of the placement (0, 1, or 2 for the sofa), since a move/rotate/resize invalidates every seat on the piece at once, not just one — a 2-seat sofa with both seats filled gets both occupants reset in one call.
- **A real bug found and fixed while building simultaneous 2-seat use**: two characters walking to the sofa's two seats at once can have their straight-line paths cross near each other close enough to collide — and since `stepToward` is fully deterministic (no randomness), the ordinary "blocked → replan to a random point" collision handling could make BOTH abandon their reserved seat, and in the worst case the two could fall into a stable mutual-blocking oscillation that never resolves on its own (reproduced directly by `furnitureUsage.test.tsx`'s "소파 좌석 2개 동시 사용" test — confirmed via a 600-tick trace that it doesn't self-resolve, it just eventually hits `MAX_FURNITURE_APPROACH_TICKS` and gives up). Fixed in `useCharacterMovementSimulation.ts`'s collision branch two ways: (1) a furniture approach is now **never** replanned to a random point when blocked — it's a specific reserved seat, not an interchangeable one; (2) a furniture approach also uses a **much lower** force-through threshold than ordinary wandering (1 blocked tick, not `MAX_STUCK_TICKS`) — since it never replans anyway, patiently waiting several ticks first (the way wandering does, to give a replan a chance) serves no purpose and is exactly what let the oscillation persist. The cost is the same already-accepted "brief visual overlap" tradeoff the doorway-stacking fix established, not a new kind of compromise.
- **Conflict prevention — cleanup called from every path that can invalidate a reservation**, wired at the same UI/orchestration call sites as phase 1 (never inside `homeStore`, to avoid a `home` → `simulation` circular import):
  - **Character deleted** — `CharacterList.tsx`'s `handleRemove` calls `releaseFurnitureUsage(id)` — releases only that character's own seat; a seatmate on the same sofa is untouched.
  - **Room deleted** — `RoomTabs.tsx`'s occupant-relocation loop and the orphan-rescue loop in `useCharacterMovementSimulation.ts` both call `releaseFurnitureUsage(character.id)` per occupant — if two occupants of the same sofa are both in the room being deleted, each is released independently as its own relocation is processed, never as a side effect of the other's.
  - **Sofa/chair deleted / moved / rotated / resized** — `evictPlacementUsage(placementId)` at every geometry-affecting mutation's own call site (`FurnitureItem.tsx`'s drag-end, `FurniturePropertiesPanel.tsx`'s X/Y/scale/variant/rotation controls and delete button, `DecorateScreen.tsx`'s keyboard `Delete`) — now clears *every* seat on the piece, not just one. A pure colorway/style/pattern change still doesn't evict (no geometry impact).
  - **Conversation starting** — unchanged: `runConversation` calls `standUp` on both participants before marking them `'talking'`; only the participant actually in a conversation stands, any seatmate is untouched.
  - **Mid-approach cancel** — the same `standUp` the "일어나기"/"다가가기 취소" buttons use.
- **UI** (`features/simulation/FurnitureUsagePanel.tsx`) — now renders **one row per seat** the selected piece actually has (two for the sofa, one for a chair), each independently showing either "앉기" (free) or the occupant's name + "일어나기"/"다가가기 취소" (taken). A single character `<select>` at the top (shown only with 2+ eligible candidates, same "never silently pick for the user" rule) applies to whichever seat's "앉기" gets clicked. **Eligible candidates now include a character already seated/approaching elsewhere** (unlike phase 1, which excluded anyone already using furniture) — selecting them and clicking a different, empty seat is exactly how a reassignment is triggered; their own current seat shows 일어나기/취소 instead of 앉기, so they can never double-book. The candidate list is sorted so **not-yet-seated characters always come first** (and are what a click defaults to without touching the picker) — a real bug caught by `furnitureUsage.test.tsx`'s "한쪽 좌석이 이미 찼어도 다른 캐릭터가 빈 좌석에 접근할 수 있다" test: without this ordering, clicking "앉기" on an empty seat with the default selection could silently steal an already-seated character off their current seat instead of seating the free one, just because of roster order. Seat labels ("왼쪽 좌석"/"오른쪽 좌석"/"좌석") are derived from each slot's own `offsetX` sign, not a hardcoded id match, so the labeling works for any future multi-seat piece too.
- **Character rendering needs no changes**, same as phase 1 — `'seated'` already has its own CSS class; front/back layering against furniture backrests remains an honest, disclosed non-goal (characters render above all furniture unconditionally, a pre-existing simplification, not something this feature changes). Two seatmates never visually overlap each other, though: the sofa's two seat offsets are 79 units apart (`±39.5` from center), and a chair only ever has one occupant — well outside two characters' combined collision diameter, so no new z-index logic was needed for this.
- **Not built (as of phase 2)**: `sofa-long`'s 3 seats or `sofa-single`/`armchair`'s single seat (identified, deliberately left out — see the first bullet), automatic/idle-triggered sitting, any monologue or dialogue content aware of sitting, and real depth occlusion between a seated character and the furniture's backrest. The bed/table followed in phase 3, directly below.

### Furniture interaction, continued: lying on a bed and lingering at a table (phase 3)

Extends phase 2's sit/stand system to two more interaction kinds — **lie** (a bed) and a *consumed* **stand** (a table, whose own slots existed in the catalog since before any interaction system did, but were never wired to anything until now) — reusing the exact same engine/store/trigger/movement-tick machinery, per CLAUDE.md's own "공통 상호작용 엔진을 확장하되... 별도의 중복 엔진을 만들지 마" instruction. Still manual-only: automatic furniture use, fatigue/sleep/meal systems, and the currency system are all explicitly out of scope.

- **A new `InteractionKind`, `'lie'`** (`home/types.ts`) — the original `bed` entry's two slots (`bed-left`/`bed-right`) shipped as `kind: 'sit'` purely because `'sit'` was the only kind that existed when they were authored, well before any interaction system consumed them; they're reclassified to `'lie'` here (**offsets untouched**) so a bed is no longer accidentally swept into the sofa/chair sit flow now that both are actually wired up — before this phase, `isSittableFurniture('bed')` returned `true` and a bed was already silently clickable/"sittable" through the generic phase-1/2 code, entirely unintended and unanalyzed; this phase is what actually gives it its own, correct UI and status.
- **Which pieces got slots, checked against real geometry, not assigned blanket-style**: `bed` (2 real `'lie'` slots, pillow-center-derived, pre-existing) plus `bed-single`/`bed-double` (1 new `'lie'` slot each, `bedLieSlot()` in furnitureCatalog.ts — offsetY = −15.1, `BedBody`'s pillow block center (0.395h) minus the piece's own local origin (0.5h); offsetX = 0, centered — for `bed-double` this is the midpoint between its two real pillows, a deliberate, disclosed choice for "one person using a double bed" this phase, not an arbitrary pick). `table` (2 real `'stand'` slots, pre-existing, finally consumed) plus `dining-table` (2 new `'stand'` slots) — both left/right, not front/back; see the table-approach-direction fix below for why and for the exact derivation. `coffee-table`/`side-table`/`sofa-single`/`sofa-long`/`armchair` were checked and deliberately left with no slots — smaller occasional tables and single-seat sofas don't fit either "2인용 소파" (already decided in phase 2) or "실제 접근할 수 있는 테이블" as cleanly, and adding data for them would mean guessing geometry rather than deriving it.
- **한 캐릭터가 눕는 기능만 — enforced structurally, not by an extra runtime check**: `getUsableLieSlots(definition)` (furnitureInteractionEngine.ts) always returns **at most one** slot — `getPrimaryLieSlot`'s result, wrapped in an array — even for the original `bed`'s real two. Both `startLyingDown` and `FurnitureUsagePanel` go through this, never `getLieSlots` (the *real*, unfiltered data, kept for a later multi-occupant phase) directly. **This was a real bug caught by `furnitureUsageBedTable.test.tsx`'s "침대 사용 중 중복 요청 차단" test**: an earlier version let a second character reserve the bed's real, un-capped second slot (`bed-right`) while the first was on `bed-left` — two people lying on the same bed simultaneously, exactly what was asked not to build this phase.
- **The shared reservation/approach engine, extended, not duplicated**: `furnitureUsageTrigger.ts`'s phase-1/2 `startSitting` is now a thin wrapper around a new shared `startUsingSlot(characterId, placementId, kind, slotId?)` core; `startLyingDown(characterId, placementId)` (no `slotId` parameter at all — there's only ever one usable slot to target) and `startLingering(characterId, placementId, slotId?)` are two more thin wrappers around the same core. `standUp` (renamed in role, not in name, since every existing call site — the UI buttons, `autoDialogueTrigger.ts`'s `runConversation` — already calls it generically) now branches on the occupied slot's own `kind` for its one real behavioral difference: repositioning. `furnitureUsageStore.ts` needed **zero changes** — it was already keyed per-seat and kind-agnostic since phase 2.
- **The one real geometric difference between kinds — `resolveWalkDestination`** (furnitureInteractionEngine.ts): a `'sit'`/`'lie'` slot sits *inside* the furniture's own solid footprint (a cushion, a pillow), so the character must stop just outside it first (`resolveApproachPoint`) and only the final transition places them at the real slot directly, bypassing collision on purpose — unchanged from phase 1/2. A `'stand'` slot (a table's left/right spot) is already drawn *outside* the footprint by construction, so there's no separate approach-vs-final-position split at all — the character walks straight to it through the ordinary, fully collision-checked path, which is exactly what satisfies "테이블 위로 올라가거나 테이블 안에 캐릭터가 들어가지 않도록" without any extra guard code, not as an afterthought.

#### Table approach direction: left/right, not front/back — and an honest limit on "always escape the furniture" (follow-up fix)

The table's `'stand'` slots originally faced front/back (`table-north`/`table-south`, offset along Y) — replaced with **left/right** (`table-left`/`table-right`, offset along X) per an explicit follow-up request, so a character walks up to either side of the table instead of only its front or back. `tableSideSlots(width)` (furnitureCatalog.ts) derives the offset as `width/2 + 26` (half the piece's own width, plus the same `FURNITURE_APPROACH_CLEARANCE` margin every other approach point uses) — applied to both `table` (replacing its old inline north/south slots) and `dining-table`. `facing` points inward toward the table's center (0/east for the left slot, π/west for the right) — still data-only, since characters have no directional sprite to actually rotate, the same disclosed limitation every other slot's `facing` already has.

- **A real, reproducible geometry bug found while re-deriving this**: the north/south fallback added for the original table-approach work (pushing the destination "just past the footprint edge" when room-clamping pulled it back inside) turned out to be **mathematically inert at the default scale** — the offset was defined as exactly `half-width + clearance`, which is *identical* to the fallback's own target, so "pushing further out" just re-computed and re-clamped to the same point. Worse, for a table pushed flush against a room wall (a placement `clampToRoom` itself genuinely allows — the table's own center can sit as close as one half-width from the wall), there is **no point at all** between the wall and the table's far edge for a character to stand in — not a bug to paper over, a real geometric impossibility for that specific placement.
- **Fixed by being honest instead of forcing a fake fix**: `resolveStandDestination` (replacing the old always-succeeds `resolveWalkDestination` fallback for `'stand'`) returns `{ point, clearOfFootprint }` — `clearOfFootprint: false` when even the clamped position can't be resolved outside the furniture's own footprint. `resolveWalkDestination` still always returns *a* point (movement itself has no notion of "refuse to go"), but `FurnitureUsagePanel.tsx` treats `clearOfFootprint: false` exactly like being blocked by another obstacle — refusing to offer that slot's "다가가기" button at all and showing the same "이 자리는 다른 가구나 캐릭터에 막혀 있어서 사용할 수 없어요" reason, satisfying "접근 지점이 벽·다른 가구·캐릭터와 충돌하면 사용할 수 없는 지점으로 처리하고, 이유를 안내해 줘" for the wall case specifically, not just the furniture/character case.
- **Proactive "이 지점은 막혀 있어요" check, `stand` only**: `isWalkDestinationBlocked(destination, obstacles, otherPositions)` (furnitureInteractionEngine.ts, reusing `movementEngine.ts`'s existing `circleIntersectsRect`/`circlesOverlap`) lets the panel flag a spot as unusable *before* the user tries, whenever another piece of furniture or character is currently sitting right on top of the resolved destination — checked independently per slot, so one side being blocked never affects the other. This is new for `'stand'` only; `'sit'`/`'lie'` weren't touched by this follow-up.
- **Each side's reservation, geometry, and cleanup remain fully independent** — unchanged from the rest of phase 3's design (per-seat `bySeatKey`, `standUp` never touching a neighbor's slot, `evictPlacementUsage` clearing both at once on delete/move/rotate) — this fix only changed *where* the two slots point and *how honestly* an unreachable one is reported, not the reservation/occupancy machinery itself.
- **Test coverage** (`furnitureUsageBedTable.test.tsx`): simultaneous left+right use, same-exact-slot race (refused), coordinates after 180° rotation (the slot still called "left" in code resolves to the room's right side once mirrored — the same pre-existing behavior the sofa's seats already have, not new), a normally-placed table's both slots resolving `clearOfFootprint: true`, a wall-flush table's blocked side reported honestly (both at the `resolveStandDestination` level and through the real `FurnitureUsagePanel`), a *different* piece of furniture placed exactly on a slot's destination also flagged blocked, and the pre-existing "reaches its slot despite nearby obstacles" (force-through) test carried over unchanged.
- **Two more `MovementStatus` values, kept genuinely distinct** (characterMovementStore.ts): `'lying'` (bed) and `'lingering'` (table), alongside the unchanged `'seated'` (sofa/chair) — per CLAUDE.md's own "소파·의자 착석 상태와 테이블 머무르기 상태는 명확히 구분" requirement. All three (plus `'talking'`) are skipped from movement stepping identically. `completeFurnitureApproach`'s new `occupiedStatusFor(kind)` is the one place that maps a slot's `kind` to the right status. The **furniture-usage store's own internal status field** (`'approaching' | 'seated'`) was deliberately left as-is — it's a generic "reservation lifecycle" label ("still walking over" vs. "arrived and occupying"), never user-facing, and renaming it for symmetry would have touched every phase-1/2 test for zero behavioral gain.
- **`standUp` reposition logic, kind-aware**: for `'sit'`/`'lie'`, repositions to `resolveApproachPoint` exactly as before (the slot is inside the footprint, so leaving it unsafe isn't an option). For `'stand'`, **no repositioning happens at all** — the linger spot is already outside the footprint by construction, so moving them anywhere else on "머무르기 종료" would be a pointless, unrequested extra hop. `evictPlacementUsage` (whole-piece delete/move/rotate/resize) never repositioned anyone for *any* kind, unchanged from phase 1/2.
- **Conflict prevention — no new wiring needed for character/room deletion**: `releaseFurnitureUsage`/`evictPlacementUsage` were already fully generic (kind-agnostic) since phase 2, so `CharacterList.tsx`, `RoomTabs.tsx`, `useCharacterMovementSimulation.ts`'s orphan-rescue loop, and every geometry-mutating call site in `FurnitureItem.tsx`/`FurniturePropertiesPanel.tsx`/`DecorateScreen.tsx` correctly clean up a bed/table user with **zero code changes** — the existing calls just started reaching further. `autoDialogueTrigger.ts`'s `runConversation` needed no changes either: its existing `standUp(charA.id)`/`standUp(charB.id)` calls already stand up a lying/lingering character exactly like a seated one, for the same reason.
- **UI**: `FurnitureUsagePanel.tsx`'s per-slot row rendering (one row per interaction slot the *selected* piece has) is now driven by small per-`InteractionKind` lookup tables (button text, occupied-state text, outcome messages, picker label, which `start*` function to call) instead of sofa/chair-only hardcoded strings — **sofa/chair's own table entries are copied verbatim from before**, so their wording/behavior is provably unchanged (`furnitureUsageBedTable.test.tsx`'s own "기존 소파·의자 패널은 변경되지 않았다" test renders a sofa through the same component and checks for exactly two, unrelabeled "앉기" buttons). Bed: 캐릭터 선택 → **눕기**, occupant name + **일어나기**. Table: 캐릭터 선택 → **다가가기** (one row per stand slot, labeled "왼쪽/오른쪽 자리" by the slot's own `offsetX` sign — `slotLabel` now shares this left/right logic with sit's "왼쪽/오른쪽 좌석" instead of a separate front/back scheme, since both are X-offset-based since the table-approach-direction fix below), occupant name + **머무르기 종료**. A slot with no left/right sense at all (a bed's single slot, or a one-seat chair) renders no side label — nothing to disambiguate.
- **Not built**: automatic/idle-triggered lying or lingering, any monologue/dialogue content aware of either, `bed`'s real second lie slot (two people sharing a bed), `coffee-table`/`side-table` linger spots, and sleep/fatigue/meal or currency systems of any kind (none of this was in scope — see the top of this section).

### Automatic furniture use (phase 4): characters occasionally use furniture on their own

Extends phase 2/3/F's manual-only sit/lie/stand system with a no-user-command background behavior — a character occasionally walks to a free sofa/chair/bed/table slot on its own, uses it for a while, then returns to normal wandering. Per its own spec's explicit scope limit, this phase implements **only** automatic selection/approach/use/ending — no currency, fatigue, sleep-drive, meal, or new-animation systems were started.

- **Reuses the existing, already-verified furniture-use functions — never a duplicate auto-only engine** (per the spec's own "자동 행동 전용 착석·눕기 엔진을 새로 복제하지 마"): `features/simulation/autoFurnitureUseTrigger.ts` calls `startSitting`/`startLyingDown`/`startLingering`/`standUp` (all unchanged, `furnitureUsageTrigger.ts`) exactly like a manual click would. Real, collision-checked walking, force-through-on-blocked, arrival detection, and seating (`completeFurnitureApproach`) are **100% already handled by the existing movement tick** regardless of whether a reservation was manually or automatically initiated — `furnitureUsageStore` has no notion of "who started this." This is why the auto trigger itself is small: it only ever decides *when* to call the existing start function and *when* to call the existing `standUp`.
- **A new, separate ephemeral store just for "is this session mine, and when should it end"** (`autoFurnitureUseStore.ts`, not persisted): `activeByCharacter` (placementId/slotId/roomId/`standUpAt`, null while still approaching), plus per-character success-cooldown (`lastEndedAtByCharacter`) and failure-retry-cooldown (`lastFailedAtByCharacter`) timestamps and a small recently-used-placement history (`recentPlacementIdsByCharacter`, size 1) for repeat-suppression. Deliberately separate from `furnitureUsageStore` (the one real reservation/occupancy ledger every manual and automatic use shares) the same way `monologueStore` stays separate from `dialogueStore`'s conversation-tracking fields.
- **Single entry point, mirroring `runMonologuePass`'s own hook-point pattern exactly**: `runAutoFurnitureUsePass(now)` (`autoFurnitureUseTrigger.ts`) is called once per movement tick from `useCharacterMovementSimulation.ts`'s `tick()`, after encounter/conversation handling and before `runMonologuePass` — no timer of its own, reuses the one existing simulation tick, and is the *only* place in the codebase that starts or ends an automatic furniture-use session. For each character: **reconcile** any in-progress auto session first, and only a character with none *after* that is considered for starting a new one — guaranteeing no same-tick double-start.
- **The `stillActive`-guard pattern, applied to furniture instead of conversations**: `reconcile()` compares its own `activeByCharacter[characterId]` against the real `furnitureUsageStore.byCharacterId[characterId]` every tick. A mismatch (seat released or reassigned by *anything* else — a manual override, `runConversation`'s own `standUp` calls on conversation start, `evictPlacementUsage`/`releaseFurnitureUsage` from any deletion/move/rotate/relocation call site, or the movement tick's own approach-timeout release) means something already changed the character's real state — `reconcile` then only forgets its own stale bookkeeping (`endAuto` if they'd gotten to use it for a while, `markFailed` if they never arrived) and **never** calls `standUp` again, exactly mirroring `runConversation`'s own `finally` guard (`if (conversationId in activeConversations)`) for the same reason: a late/duplicate action must never redo work something else already did or clobber a newer, unrelated state. This is what lets every existing cleanup path correctly cancel an in-progress or completed auto session with **zero changes** to any of them — `CharacterList.tsx`, `RoomTabs.tsx`, `FurnitureItem.tsx`, `FurniturePropertiesPanel.tsx`, `DecorateScreen.tsx`, `autoDialogueTrigger.ts`'s `runConversation`, and the movement tick's own orphan-rescue/approach-timeout logic none of them know or need to know this feature exists.
- **The one addition to an existing cleanup call site**: `CharacterList.tsx`'s `handleRemove` now also calls `useAutoFurnitureUseStore.getState().forgetCharacter(id)` (mirroring `monologueStore.forgetCharacter`, same rationale) — a deleted character is dropped from `characterStore` immediately, so `runAutoFurnitureUsePass`'s per-character loop (which iterates `characterStore.characters`) would never visit that id again to reconcile its own bookkeeping away on its own. Not needed for room deletion (a room deletion doesn't remove a character — the next tick's reconcile cleans up naturally once `releaseFurnitureUsage`/`moveCharacterToRoom` have run).
- **Start conditions** (`autoFurnitureUseTrigger.ts`'s `tryStart`, plus `autoFurnitureUseEngine.ts`'s `rollShouldStartAutoFurnitureUse`): the "자동 가구 사용" setting is on; the character exists, is in a real room, isn't `'talking'`, isn't already seated/lying/lingering (manually or automatically), isn't `dialogueStore.isCharacterBusy`, and isn't already reserved/approaching anything; the success cooldown *and* the separate failure-retry cooldown have both elapsed; then a small per-tick probability roll.
- **Furniture selection** (`autoFurnitureUseEngine.ts`'s `collectAutoFurnitureCandidates`/`pickAutoFurnitureCandidate`): every currently-free slot (any kind — sit/lie/stand, i.e. sofa/chair/bed/table — whichever a room's furniture actually has) is gathered via the *exact same* per-kind slot getters (`getSitSlots`/`getUsableLieSlots`/`getStandSlots`) the manual trigger and `FurnitureUsagePanel.tsx` already use, so a candidate here is always something the manual path would also accept — including the bed's real-but-capped second pillow slot never being offered, and a 2-seat sofa's other seat staying usable even while one side is occupied. A character's own most-recently-auto-used placement id is soft-avoided (never picked again immediately) *unless* honoring that would leave zero candidates — e.g. only one usable piece exists in the room — in which case the exclusion is dropped so the same piece remains selectable again after its own cooldown, per the spec's explicit requirement. Picking from an empty candidate list is a silent no-op (try again next eligible tick), never a forced retry loop.
- **Full behavior flow**, all through the pieces above: start-condition check → candidate search/pick → reserve + hand off to the existing movement engine (`startSitting`/`startLyingDown`/`startLingering`) → real collision-checked walking → sit/lie/linger only on real arrival (the *existing* tick's own arrival logic, untouched) → hold for a randomized duration → `standUp` (existing) → normal idle/wandering resumes → per-character cooldown applied. A reservation lost to a same-tick race (or any other refusal) is treated as a failure (shorter retry cooldown), never an infinite immediate retry.
- **Frequency/timing** (`autoFurnitureUseConfig.ts`, calibrated against the project's own existing cadences, not invented from scratch): `AUTO_FURNITURE_USE_CHANCE_PER_TICK` = 0.0015, equal to `monologueConfig.ts`'s most conservative ('rare') preset — deliberately at least as infrequent as monologue's default tier, since walking across the room and sitting for a while is a far more visible commitment than a thought bubble. `AUTO_FURNITURE_USE_COOLDOWN_MS` = 90s (higher than dialogue's 60s and monologue's 45s 'normal' cooldowns, for the same reason). `AUTO_FURNITURE_USE_RETRY_COOLDOWN_MS` = 15s (a separate, shorter cooldown after a failed/incomplete attempt). Hold duration is randomized between `AUTO_FURNITURE_USE_MIN_HOLD_MS` (20s) and `AUTO_FURNITURE_USE_MAX_HOLD_MS` (45s) so sessions don't all look identically timed. No new timer of any kind — every value above is read only by the one existing tick.
- **Manual commands and conversations always outrank auto behavior** — enforced structurally, not by a priority flag: a manually-seated character is simply invisible to `tryStart` (already occupied/reserved), a manual reassignment mid-auto-session is picked up by `reconcile` as an ordinary "something else changed the seat" case, and a conversation starting always wins because `runConversation` already calls `standUp` on both participants before marking them `'talking'` — `reconcile` just notices the resulting mismatch next tick and cleans up its own bookkeeping, touching no movement/conversation state itself.
- **Setting UI**: one on/off toggle, "자동 가구 사용", added to `LiveScreen.tsx`'s existing frequency panel (between "혼잣말 빈도" and the relationship row) — reuses the existing `.live-pause-toggle`/`.live-frequency-header`/`.live-frequency-description` styling, no new CSS. Persisted via a new, minimal store (`autoFurnitureUseSettingsStore.ts`, localStorage key `dearly-auto-furniture-use`, `{ enabled: boolean }`, mirroring `monologueFrequencyStore.ts`'s persisted-setting-only pattern) — **default OFF**, so existing users see no behavior change until they explicitly opt in; missing/corrupt saved data also falls back to OFF. No `homeStore` schema/version bump needed — this is a brand-new, independent store, not a shape change to existing persisted data.
- **Turning the setting off only stops *new* auto sessions from starting — an in-progress one finishes naturally**, the same policy already established for a mid-conversation dialogue-frequency change ("진행 중인 대화는 자연스럽게 끝내고, 이후부터 새 빈도 적용"), applied here for consistency: `reconcile()` never reads the setting at all, only `tryStart()` does.
- **Test coverage**: `autoFurnitureUseEngine.test.ts` (pure-function unit tests — the frequency gate's every branch, candidate collection/filtering including the bed's capped slot and skipping unknown furniture, repeat-suppression including the single-piece fallback, hold-duration range) and `autoFurnitureUse.test.tsx` (full integration, real stores + a real movement tick under fake timers, injectable `Math.random` for determinism): default-off, persists across a simulated reload, valid furniture auto-selected and actually walked to, already-reserved seats never targeted, simultaneous independent 2-seat-sofa use, no usable furniture handled without a retry storm, automatic stand-up + resumed wandering after the hold duration, per-character-independent cooldowns, repeat-suppression (including the single-furniture-piece exception), safe shorter-cooldown retry after an approach timeout, manual furniture use taking priority (both "already manually using something" and "manually reassigned mid-auto-session"), a conversation starting during an auto session ending it cleanly, no interference with a concurrent, unrelated pair's auto-dialogue, furniture deletion/move/rotation cleanup, character deletion cleanup (`forgetCharacter`), room-deletion relocation cleanup, and confirmation that no auto-session runtime state (only the on/off setting) is ever persisted.

### Room decor presets: six starter themes, applied as one safe, backed-up, revertible swap

A "방 프리셋" (room theme preset) is a complete room look — wallpaper + floor + a real furniture combination and layout — applied to the active decorate room in one step, from a new "테마" tab (`DecorateScreen.tsx`, alongside 가구/벽지/바닥). Built entirely on top of the existing wallpaper/floor/furniture/collision/furniture-interaction/auto-furniture-use systems above; nothing here is a new rendering path or a new schema.

- **Data** (`decorPresets.ts`): `DecorPresetDefinition` — id/name/description/`category` (`princess`/`vintage`/`simple`/`fantasy`/`lifestyle`, distinct from `RoomKind` and from the legacy `RoomTheme`/`roomThemes.ts`, which stays untouched, kept only as the old v2 schema migration's color source)/`tags`/`accentColors` (cosmetic card swatches)/`wallpaper`/`floor` (the real `WallpaperSettings`/`FloorSettings` types, unchanged)/`furniture` (a list of `DecorPresetFurnitureEntry`). Every `furnitureId` is a real `furnitureCatalog.ts` id and every `colorway` is checked against that piece's real `getColorwayOptions()` — no invented ids, no fake colors, no new SVG art (out of scope, per spec). A furniture entry's position is stored as `xRatio`/`yRatio` (0-1, a fraction of `ROOM_WIDTH`/`ROOM_HEIGHT`), not a raw absolute coordinate — `decorPresetEngine.ts`'s `resolveDecorPresetFurniture` is the one place that multiplies back out against the room's *current* logical size. Every room in this app shares one fixed logical size today, so this makes no visible difference yet, but it's what "모든 방에 동일한 절대좌표를 무조건 적용하지 마" asks for structurally — if the room's own logical size (`roomLayout.ts`) is ever made configurable, every preset keeps landing in the same *relative* spot instead of drifting off an edge.
- **Six themes** (딸기우유 공주방/화이트 엔젤 룸/로맨틱 빈티지 룸/러블리 카페 룸/심플 모던 룸/토끼 인형방), each a genuinely different furniture *combination*, not a recolored copy of the same layout — checked directly (`decorPresets.test.ts`'s "6종 모두 서로 다른 가구 조합을 가진다"). Layouts were hand-placed and then verified — not just eyeballed — against the real engine: every solid piece's `furnitureObstacles` rect is checked pairwise for overlap, the room's one fixed doorway point is checked clear, every solid floor piece's bottom edge is checked to actually be on the floor's own surface (see the follow-up fix below), and every piece that actually has a real interaction slot (only `bed-single`/`bed-double`/`dining-table`/`dining-chair`/`office-chair` do — most catalog entries past the original six declare none) has its `resolveWalkDestination`/`resolveStandDestination` point checked against `isWalkDestinationBlocked` with every *other* piece in the same preset. Several pieces carry an optional `patterns` override (a floral bed blanket, a gingham café chair seat, a heart-print bunny-room blanket, …) on top of their `colorway`, using the exact same per-placement `colors`/`patterns` mechanism `FurnitureStyleEditor.tsx` already exposes for manual editing — nothing new was added to support this, only real preset data using an existing field.
- **Engine** (`decorPresetEngine.ts`): `validateDecorPreset` checks a preset's furniture ids/colorways/variants/`colors`/`patterns` against the real catalog (a pattern's surface id must be one of that piece's real `patternSurfaces`, a color override's part id one of its real `colorParts`) and a generic "does this piece's own base size even fit the room at all" check against the actual `ROOM_WIDTH`/`ROOM_HEIGHT` constants — honestly disclosed as structurally unreachable today (every room is the same fixed size, so nothing can ever fail this specific check with the six hand-authored presets), but a real, generically-implemented guard rather than a fake scenario, satisfying the spec's "방 크기 때문에 프리셋을 정상적으로 적용할 수 없다면... 이유를 안내" for whenever that stops being true. It also refuses a preset entry outright if its position would need *any* adjustment at all once resolved (see the follow-up fix below) — never silently relocates a piece. `resolveDecorPresetFurniture` resolves ratios → real coordinates, clamps every piece through the same shared pipeline manual placement uses (see below), and mints a fresh `crypto.randomUUID()` per piece per call — applying the same preset twice, even across different rooms, never collides on placement id.
- **Apply/backup/revert** (`decorPresetApply.ts`, `roomDecorBackupStore.ts`) — targets the active decorate room the same *implicit* way every existing decorate-phase mutator already does (via `activeDecorateRoomId`), which is what makes "다른 방의 가구와 설정을 변경하지 않는다" hold for free, with zero room-scoping code of its own. Order: validate (no mutation yet) → back up the room's current wallpaper/floor/furniture into `roomDecorBackupStore` (ephemeral, not persisted, one entry per room, overwritten by the next apply — a **single step back**, not a multi-level undo history, explicitly disclosed in the panel's own hint text and the apply confirmation dialog) → end furniture usage on every existing placement (`evictPlacementUsage`, the exact function every furniture delete/move/rotate call site already uses — no duplicate cleanup path) → **one** atomic commit (`homeStore.ts`'s new `applyRoomDecor` action, replacing wallpaper+floor+furniture together in a single `set()`) → reposition any character currently in that room whose position now collides with the new furniture (`movementEngine.ts`'s existing `pickRandomDestination`/`furnitureObstacles`/`circleIntersectsRect`, never a new placement algorithm; never deletes a character or moves it to a different room). Nothing before the atomic commit touches persisted state at all, so a validation failure or a thrown exception anywhere before it leaves the room completely untouched — there is no partial-apply state to roll back from, because nothing partial can ever be written. `revertLastDecorPreset` is symmetric and restores the backed-up placements' **original ids** (never re-minted, since those exact ids were freed the moment the preset replaced them). `applyRoomDecor` needed **no `SCHEMA_VERSION` bump** — it's a new way to construct/replace a room's existing fields, using the exact same `Room`/`FurniturePlacement`/`WallpaperSettings`/`FloorSettings` shapes; nothing about what gets persisted changed.
- **Auto-furniture-use needs no special-case cleanup call at all**: a preset replacing the furniture a character was auto-using is just another instance of "the seat `autoFurnitureUseStore` was tracking no longer matches `furnitureUsageStore`" — `autoFurnitureUseTrigger.ts`'s existing `reconcile()` already discovers and cleans this up on its own on the very next movement tick, the same `stillActive`-guard pattern it already uses for manual overrides, conversation starts, and every other furniture delete/move/rotate. This is deliberate, not an oversight: adding a proactive auto-furniture-use cleanup call here would be a second, redundant cleanup path for something the existing one-tick-later self-healing already covers correctly (verified directly — `decorPresetApply.test.tsx`'s own "자동 가구 사용 중인 캐릭터가 있어도..." test).
- **UI** (`DecorPresetPanel.tsx`, `DecorPresetPreview.tsx`): a filterable card grid (전체/공주/빈티지/심플/판타지/생활감) in the 연분홍 theme (existing `--accent`/`--border`/`--panel-bg`/`--panel-selected-bg` tokens only, no new colors), each card showing name/description/accent-color swatches/tags/미리보기/적용. `DecorPresetPreview.tsx` renders `resolveDecorPresetFurniture(preset)`'s own output (not a second, independent position calculation — see the follow-up fix below) through `WallSurface`/`FloorSurface`/`FurnitureIcon` exactly the way `Room.tsx` composes them, but reads only from the `preset` prop passed to it — never `useHomeStore` — so opening or closing the preview modal can never touch the real room; there is no separate static preview-image step, since this *is* the same rendering path the real room uses once a preset is actually applied. Clicking "적용" (on a card or inside the preview modal) always shows a `window.confirm` dialog with the spec's own wording (mentioning the backup and the one-time revert) before calling `applyDecorPreset` — selecting or merely previewing a preset never mutates anything on its own.
- **Not built**: "내 프리셋 저장" (saving the *current* room as a reusable preset), preset sharing, random preset recommendation, new furniture/SVG art, and any currency system — all explicitly out of scope for this phase, per the spec's own "다음 단계는 시작하지 말고 내 승인을 기다려 줘".

#### Fixing "가구가 벽에 떠 있는" — a shared, zone-aware placement pipeline (follow-up fix)

A real, user-reported browser bug: applying a preset could leave furniture reading as if floating against the wall, with no floor surface visibly under it. Root cause, found by tracing the actual render math rather than nudging coordinates: `roomLayout.ts`'s `clampToRoom` (used by every placement path — manual drag, the properties panel's X/Y inputs, the catalog's auto-add grid, and the original preset resolver) only ever bounded a placement to the room's *outer* edges. It never distinguished "this piece stands on the floor" from "this piece hangs on the wall" — so a floor piece with too small a Y rendered with its own ground-contact shadow/legs up in the *wall* visual band (above `FLOOR_HEIGHT_RATIO`'s own boundary), with no floor under it. This affects manual placement identically (dragging a sofa up near the ceiling looks exactly the same way) — not only presets, which is why the fix lives in a shared module, per the spec's own "수동 배치와 프리셋 적용이 동일한 좌표·표면·경계 규칙을 사용하도록".

- **`furniturePlacementEngine.ts`** is the one shared placement pipeline every positioning call site now goes through: `FurnitureItem.tsx`'s drag-end, `FurniturePropertiesPanel.tsx`'s X/Y/scale/variant handlers, `placementDefaults.ts`'s `defaultPlacementPosition` (the catalog's initial-placement grid), and `decorPresetEngine.ts`'s `resolveDecorPresetFurniture`. `placementBounds(definition, width, height)` computes the valid center-point range; `clampFurniturePlacement` clamps into it; `isPlacementWithinBounds` reports whether a point would need any adjustment at all (used by `validateDecorPreset` to refuse rather than silently relocate — see below).
- **Only a real, floor-standing, solid piece is affected**: the rule only raises `minY` for `zone: 'floor'` pieces with `collision.mode === 'solid'` — a `'wall'`-zone piece (window, frame, wall-clock, curtain, floor-mirror) keeps its already-established, deliberate "moves freely anywhere after its initial placement, no snapping or range limit" behavior unchanged, and a `'floor'`-zone piece with `collision: 'none'` (a mug, vase, book stack, table lamp, or doll — routinely placed resting *on top of* another piece of furniture, at whatever height that surface happens to be) is equally exempt, since forcing those down to the literal floor would be wrong, not a fix. `floorFurnitureMinY(height)` is `max(height/2, FLOOR_SURFACE_TOP_Y - height/2)` — the minimum center-Y whose *bottom edge* (`y + height/2`, the exact same bottom every furniture illustration grounds its shadow/legs against, and the same one `furnitureInteractionEngine.ts`'s `footprintRect`/`movementEngine.ts`'s `furnitureObstacles` already compute) doesn't rise above the floor's own visual top edge (`FLOOR_SURFACE_TOP_Y`, the same `ROOM_HEIGHT * (1 - FLOOR_HEIGHT_RATIO)` formula `movementConfig.ts`'s own `FLOOR_TOP_Y` uses for character-walking bounds — recomputed independently so `home` never has to import from `simulation`).
- **`validateDecorPreset` never silently relocates a piece**: an entry whose authored `xRatio`/`yRatio` would need *any* adjustment (clamped to the room's outer bounds, or pushed down by the floor-grounding rule) fails validation outright with a clear reason, exactly satisfying the spec's "적용할 수 없는 가구가 발견되면 기본적으로 적용을 중단하고... 기존 방은 그대로 유지". The spec's further "가구 일부를 제외하거나 자동으로 다른 위치에 배치하는 대체 적용은 사용자가 변경 내용을 미리 확인하고 명시적으로 승인했을 때만 허용" describes an *optional* escape hatch (approve-the-adjusted-result) that was **not built** — every one of the six built-in presets is authored precisely enough to need zero adjustment at all (proven by `decorPresets.test.ts`), so that path is never actually reachable with the shipped presets, and a whole separate confirm-the-diff UI for a scenario nothing in this app can currently trigger would be speculative complexity ahead of any real need.
- **`DecorPresetPreview.tsx` now renders from `resolveDecorPresetFurniture(preset)`'s own output**, not a second, independently-recomputed position formula — the old version did the ratio→coordinate math inline itself, with no clamping at all, which could genuinely disagree with what got applied. Calling the one real resolver is what guarantees "미리보기와 실제 적용은 동일한 배치 결과를 사용" structurally, not by keeping two implementations in sync by hand.
- **`placementDefaults.ts`'s catalog-add grid** (`defaultPlacementPosition`) also moved its `GRID_ORIGIN_Y`/`GRID_SPACING_Y` from 110/110 to 300/90 — already comfortably inside the floor-grounding range for typical floor-furniture heights, so a freshly-added piece reads as standing on the floor from the moment it appears, rather than relying entirely on the clamp to rescue a bad starting point after the fact.
- **Six presets' coordinates were fully redesigned**, not nudged — every solid floor piece across all six themes now genuinely satisfies its own `floorFurnitureMinY`, re-verified geometrically (obstacle overlap, doorway clearance, interaction-point reachability) exactly the same way the original layouts were, plus a new explicit floor-grounding assertion in `decorPresets.test.ts`.

### Furniture visual renewal + catalog expansion (phase 5): a shared sheen primitive, `lightSource` metadata, and four new pieces

#### Follow-up (phase 5b): material naming, an `interactionType` classifier, a `storage` category, 10 more pieces, and safe size-variants

A second, larger expansion pass, once the earlier phase-5 renewal/presets/lighting were confirmed working in a real browser. Same discipline: existing furniture movement/collision/sit-and-stand-up/auto-use logic, `furnitureUsageStore`'s shape and API, and every furniture added so far (dresser, candle, canopy-bed, round-table) are all **untouched** — everything here is additive catalog data plus new illustration files.

- **Material naming** (`palette.ts`): `MATERIAL_TONES` (wood/glass/metal/ceramic) is a naming layer over tones that mostly already existed (`taupe` was already every wooden leg's tone; `glass`/`metal` already existed) — `ceramic` is the one genuinely new tone. - **Why a bigger dining table is a separate catalog id, never a `variants` entry — a real correctness pitfall found and avoided, not just a style choice**: `FurnitureInteractionSlot.offsetX`/`offsetY` are baked into a definition at catalog-authoring time from that definition's **own base `width`/`height`** (e.g. `tableSideSlots(176)` for `dining-table`) — but a `variants` entry only changes the *rendered/footprint* size via `getFurnitureSize(definition, placement.variant)`; it never recomputes `interactionSlots`. Giving `dining-table` a bigger `variants` entry would silently leave the stand points positioned for the *original* (smaller) width on the bigger variant — landing too close to (or inside) the larger table's own footprint. `dining-table-large` sidesteps this by being its own definition with its own `tableSideSlots(240)` call, exactly the same reasoning the original `table`/`dining-table` split already established. **`variants` stays safe exactly where it was already used** — pieces with zero `interactionSlots` (`rug`, and now `plant`'s 보통/큰 화분 and `dresser`'s 2단/3단, both added this phase) have no slot-offset to ever get wrong.

- **UI**: `FurnitureCatalogPanel.tsx`'s existing "사용 가능" badge (from phase 5) already covers every new seat/lie/table-with-real-slots piece correctly with zero changes, since it already keys off `isInteractableFurniture` — the interactionType classifier and the badge are two independent things that happen to agree, not one driving the other.
- **Not built**: any change to `furnitureUsageStore`/movement/collision/auto-furniture-use APIs (none were touched), a UI surface for `classifyInteractionType` beyond existing behavior (no new filter control was added — the classifier exists for future use and as an internal completeness-tested mapping), and a decorative (non-sittable) second ottoman — the spec's "오토만 중 실제로 앉을 수 있는 것" nuance is satisfied structurally (any future decor-only ottoman would simply declare no `interactionSlots`, exactly like every other decor piece already does), not by shipping two ottomans this round.

### Time-of-day room lighting: a scoped visual overlay, reusing BGM's own time band

`src/features/lighting/` — the room (and only the room) gradually brightens/dims over the day, as a purely visual effect layered on top of the existing wall/floor/furniture rendering. **Never touches wallpaper/floor/furniture/preset color data** — see "Room decor presets" above for why that separation matters (stage 5 of the spec that requested this explicitly required the two features not affect each other's data, and they're structurally incapable of it: this module never calls a single `homeStore`/`decorPreset*` mutator).

- **Reuses BGM's own existing time band — per the spec's own "조명과 BGM은 반드시 동일한 시간 기준을 사용해야"**: `TimeBand`/`getTimeBand`/`getCurrentHour` come straight from `bgm/bgmConfig.ts`/`bgm/timeBand.ts` (아침 05-10, 낮 11-16, 저녁 17-20, 밤 21-04) — a *second*, independently-boundaried band system (the spec's own fallback boundaries, 06-10:59/…) was deliberately never built, since a real one already exists and the spec's own instruction is to prefer it. `RoomLightingOverlay.tsx` reads `bgmStore`'s `currentBand` — the exact shared value `useBgmController.ts`'s own periodic real-clock hour-check (`BGM_HOUR_CHECK_INTERVAL_MS`, mounted once in `App.tsx`) already keeps current — rather than rolling a second timer of its own, per the spec's own "조명만을 위한 불필요한 반복 타이머는 만들지 마". A direct `getTimeBand(getCurrentHour())` fallback covers only the brief instant before that controller's first effect has run (`currentBand` starts `null`).
- **Tints** (`roomLightingConfig.ts`'s `ROOM_LIGHTING_TINTS`): 아침 a warm soft `soft-light` tint (adds warmth without much darkening), 낮 **literally no tint at all** (`baseOpacity: 0`, implementing "원래 색감에 가까운 밝기" exactly rather than an arbitrarily-small nonzero value), 저녁 a pink/orange `multiply` tint, 밤 a stronger deep-indigo `multiply` tint. `multiply` (not a flat color, not a higher-opacity solid) is what keeps furniture shapes/colors identifiable even at night's highest opacity — it scales each underlying pixel's own color down proportionally rather than crushing everything toward one flat tone, satisfying "밤에는 확실히 어두워지지만 검게 뭉개지지 않음". `roomLightingEngine.ts`'s `getRoomLightingStyle(band, intensityPercent)` is the one pure function resolving a band + the user's 0-100% intensity setting to a real CSS style; the intensity multiplies each band's own `baseOpacity` linearly, so 0% is always fully invisible and 100% is exactly that band's authored baseline, for any band.
- **Rendering** (`RoomLightingOverlay.tsx` + `.css`): mounted as the very last child of both `Room.tsx` (decorate) and `LiveRoomView.tsx` (live) — a single absolutely-positioned `<div>` with `pointer-events: none` (never intercepts a click/drag/keyboard event meant for furniture underneath — "조명 레이어는 클릭·드래그·선택 이벤트 차단 금지"), a high `z-index` (above every furniture/character token in that room's own stacking context), and a CSS `transition` on `background-color`/`opacity` — this *is* the entire "부드러운 변화" implementation, no JS interpolation loop, no extra timer. Renders **nothing at all** (`null`) while the setting is off, so "기본값은 꺼짐" costs precisely zero DOM/style overhead. It touches no wallpaper/floor/furniture DOM at all, so every furniture SVG's own shadow/outline/pattern (drawn inside that SVG) is completely unaffected underneath it, satisfying "기존 가구 그림자·테두리·패턴 보존" for free.
- **Scope, not a global CSS filter**: mounted only inside `.room`/`.live-room`, never at the app or `<body>` level — this is what makes "기존 연분홍 UI와 대화창은 어두워지지 않아야" and "전체 앱에 CSS filter를 적용하지 마" hold structurally. `RoomTabs`, the settings panels, the dialogue feed, tooltips, and every editing control live entirely outside the room's own DOM subtree and are never touched.
- **Settings** (`roomLightingSettingsStore.ts`, localStorage key `dearly-room-lighting`, mirrors `autoFurnitureUseSettingsStore.ts`'s persisted-setting-only pattern): `enabled` (default **off**) and `intensity` (0-100, default 70). UI lives in `LiveScreen.tsx`'s existing settings panel, alongside 자동 가구 사용's own toggle — a 켜짐/꺼짐 button (both toggles' buttons now carry a distinguishing `aria-label`, since they share the exact same visible "켜짐"/"꺼짐" text), an intensity slider shown only while enabled, and four always-visible 아침/낮/저녁/밤 preview swatches. The swatches call `getRoomLightingStyle(band, 100)` directly on small standalone `<span>` boxes — they never touch the real room, the real game time, or `bgmStore` in any way, satisfying "미리보기는 실제 게임 시간이나 BGM을 변경하지 않아야" by construction (not by a guard that could be bypassed, since there's simply no code path from the swatches to any of that state).
- **Stage 5 (preset/lighting non-interference), verified directly, not just asserted**: applying/reverting a preset never reads or writes `roomLightingSettingsStore`; toggling/adjusting lighting never reads or writes `homeStore`/`decorPresetApply.ts`'s backup store — the two modules simply never call into each other at all. `DecorPresetPreview.tsx` never mounts `RoomLightingOverlay`, so a preset preview always shows the theme's true, undimmed colors regardless of the real current time band or the lighting setting.
- **Not built**: per-room lighting overrides (one global setting for every room, matching how `bgmEnabled`/`dialogueFrequencyStore`/etc. are already app-wide, not per-room), and a richer "반복 설정"-style multi-mode beyond the single intensity slider — neither was requested.

### Auto-dialogue engine: encounter-triggered, personality/relationship-weighted, multi-pair-safe

**Never calls any external API — there is no AI integration left in this project at all** (see "There is no AI/API integration" above). Auto-dialogue draws from each character's pre-registered `CharacterDialogueLine` library (`aiProfile.dialogueLines`) **first**, falling back to the built-in default dialogue library (below) whenever that isn't enough to fill a whole conversation — registering example lines is now fully optional, not a prerequisite for either auto or manual dialogue to work.

- **Central config** (`autoDialogueConfig.ts`): `DIALOGUE_FREQUENCY_PRESETS` (5 modes: `quiet`/`occasional`/`normal`/`chatty`/`rowdy`, each a `{ chancePerEncounter, cooldownMs }`), `BUBBLE_REVEAL_INTERVAL_MS`, `PAUSE_POLL_INTERVAL_MS`, `RECENT_LINE_HISTORY_SIZE`, `MIN_BUNDLE_LINES`/`MAX_BUNDLE_LINES`. Both the "대화 빈도" panel (`LiveScreen.tsx`) and the engine read these — the numbers must never be duplicated elsewhere. `chancePerEncounter` is rolled once per real proximity event (not a fixed timer — see above), so the actual real-time conversation frequency also depends on how often characters happen to wander near each other; the mode descriptions deliberately don't promise a specific average time for this reason. `cooldownMs` is a hard floor per-pair (not global), which is what actually prevents 'rowdy' from producing a runaway loop between two characters who just keep standing next to each other.
- **Personality weighting** (`character/personalityTags.ts`): 71 built-in tags across 6 categories (기본 성향/대인관계/감정 표현/행동과 생활/대화 성향/관계에서의 태도 — `PERSONALITY_CATEGORY_*`), each with an `initiateWeightDelta` (who speaks first), a `startChanceDelta` (how much this character's presence raises/lowers a pair's odds of starting a conversation at all — see `rollShouldStartConversation` below), a `behaviorWeightDelta` (movement behavior bias, see the movement section), and a `lineAffinity` scorer. **Only a small, explicitly-named subset of the 71 have any non-zero effect** (`OVERRIDES` in that file) — 사교적/활발함/수줍음/내향적/차분함/게으름/호기심/수다스러움/과묵함/직설적 plus the original 4 line-affinity tags (다정함/무뚝뚝함/장난스러움/차분함). Every other tag is honestly neutral: label/category/description only, ready to be connected later but not silently claiming an effect it doesn't have. Multiple tags always sum rather than any one overriding the others, and zero tags means the neutral weight (1) everywhere — never zero, never blocked. The line-affinity and keyword-based heuristics are **best-effort**, not guaranteed matches — disclosed, not assumed perfect.
- **Relationship weighting** (`dialogue/relationshipConfig.ts` + `relationshipStore.ts`): **per-pair** `relationshipType` (romantic/close/friend/family/rival/awkward), resolved via `relationshipStore.getRelationshipType(idA, idB)` (order-independent, `pairKey.ts`), multiplies that specific pair's start chance and **hard-excludes** romantic-tagged lines for that pair unless its type is `romantic` (`isRomanticLine` — another best-effort keyword heuristic over `tags`/`emotion`, but the exclusion itself is a hard filter, not a soft downweight). `LiveScreen.tsx` has a pair-picker (only shown when there are 2+ pairs to choose from) next to the relationship-type select. There is no pre-existing structured "relationship type" or numeric intimacy score this reuses (only the free-text `aiProfile.relationship` and `tone.addressForPartner` fields existed, and those stay as-is, AI-prompt-only) — this is a new, explicitly-introduced setting.
- **Engine** (`autoDialogueEngine.ts`) — pure functions, every probability/selection function takes an injectable `random: () => number = Math.random` so tests can be deterministic. Unchanged in shape from the pre-movement version — it already operated on a generic pair, never assumed which 2 out of how many total characters, so extending to 5 characters/10 pairs needed no changes here, only to how callers resolve relationship type and cooldown (per-pair now, not global):
  1. `rollShouldStartConversation` — frequency-mode gate (chance 0 in `quiet` short-circuits immediately, before any multiplier is ever computed) → that pair's cooldown gate → a roll weighted by both the relationship multiplier *and* `startChanceWeightFor()` for each participant's resolved tags (수다스러움/사교적 raise it, 과묵함/수줍음 lower it) — no personality combination can produce auto-dialogue in quiet mode, since the gate above already returned.
  2. `pickFirstSpeaker` — personality-weighted pick of which of the two speaks first.
  3. `buildAutoDialogueBundle` — first **tries the registered-line path** (`tryBuildFromRegisteredLines`, unchanged in behavior from before the default library existed): 2-4 lines (`MIN_BUNDLE_LINES`-`MAX_BUNDLE_LINES`), alternating speakers starting from the first speaker, each turn filtered by: not `conflict`/`reconciliation` category (auto-dialogue never invents an argument — there's no tracked prior-conflict state to make that coherent), real-clock time-of-day gating (see below), romantic-line exclusion per that pair's relationship type, and per-character recent-use exclusion (falls back to `isFallback` lines, recency-exempt, if nothing else qualifies) — then personality-affinity-weighted random selection among what's left. **If that fails to fill even one turn** (including a character with zero registered lines at all — the common case now), falls back to the default dialogue library instead of returning `null` immediately — see below. Only returns `null` (skip the whole conversation) if *even the default library* has nothing eligible for the current relationship/time, which in practice essentially never happens (several default categories are always time/relationship-neutral).
- **Trigger** (`autoDialogueTrigger.ts`'s `attemptEncounterConversation(idA, idB, ...)`) — called exactly once per rising-edge encounter by `useCharacterMovementSimulation.ts`, never on a timer. Resolves that pair's relationship type and cooldown, rolls/builds as above, and on success marks both characters `'talking'` in `characterMovementStore` (pausing their movement) for the duration. Bubbles reveal one at a time via `appendLines` with a `BUBBLE_REVEAL_INTERVAL_MS` delay between each; before each bubble, `waitWhileNotRunning` polls `simulationStore.isRunning` and blocks (both the reveal delay and the next line are suspended, not just visually hidden) until resumed. A frequency-mode change mid-conversation never aborts the in-progress bundle (only the *next* encounter's gate re-reads the new mode), matching "진행 중인 대화는 자연스럽게 끝내고, 이후부터 새 빈도 적용".
- **No character in two conversations at once, and disjoint pairs can converse concurrently** (`dialogueStore.ts`): `activeConversations` is `Record<conversationId, string[]>` (participant ids), not a single flag, so several disjoint pairs (e.g. A/B and D/E among 5 characters) can each hold their own entry at the same time. `isCharacterBusy(id)` checks every entry's participant list. `startConversation(participantIds)` is the single choke point — it refuses (returns `null`) if **any** intended participant is already in another entry, so a third character encountering an already-talking pair can never force its way in or cause a duplicate. `endConversation(conversationId, pairKey)` removes that entry and stamps `lastConversationEndAtByPair[pairKey]` — cooldowns are per-pair, not global, which is what lets one pair go quiet while a different pair keeps talking. This is exercised directly by `useCharacterMovementSimulation.test.tsx`'s multi-character tests (3 mutually-close characters never double-book the third; 5 characters with two disjoint close pairs converse at the same time).
- **Recent-use tracking** (`dialogueStore.ts`, not persisted — ephemeral runtime state, same rationale as the conversation-tracking fields above): `recentAutoLineIdsByCharacter` (last `RECENT_LINE_HISTORY_SIZE` line ids per character — populated for both registered lines and default-bundle turn ids, so recency tracking is uniform regardless of source) and, **kept as a genuinely separate record** per spec, `recentDefaultBundleIdsByPair` (last `RECENT_BUNDLE_HISTORY_SIZE` default-bundle ids per *pair*, `pairKey`-keyed) — only ever written when a conversation actually used the default-library fallback.

### Default dialogue library: pre-written conversation bundles for characters with no registered example lines

`features/dialogue/defaultDialogueLibrary.ts` exists because requiring every character to have hand-written example lines before auto/manual dialogue works at all was too high a bar — the built-in library makes dialogue work out of the box from personality + relationship + time-of-day alone. This is genuinely new content, not a fallback stub: **33 bundles** as of this writing, spanning every category the spec named except `conflict`/`reconciliation` (deliberately excluded — see below).

- **A bundle is a whole, pre-written, connected exchange (`DefaultDialogueBundleDef`), never independent lines stitched together at random.** Each has an `id`, a `categoryId` (one of `situationCategories.ts`'s ids — see below for the new ones added alongside the original 10), an optional `relationshipTypes` restriction (undefined = usable for any relationship type, covering both "관계 미설정" and the "동료"-style everyday-pair case this app doesn't model as a distinct type), an optional `romantic` flag (hard-excludes the bundle unless the pair's relationship type is exactly `'romantic'` — authored explicitly, not keyword-guessed the way `isRomanticLine` has to for free-text user lines), and 1-4 `turns`, each tagged `speaker: 'first' | 'second'` (resolved at runtime against whichever character actually speaks first) plus `emotion`/`tags` (so the *existing* personality `lineAffinity` heuristics score default turns exactly like registered `CharacterDialogueLine`s — no new personality-weighting mechanism was needed for this).
- **`buildAutoDialogueBundle`'s fallback selects one whole bundle, never per-turn** (`pickDefaultBundle`/`autoDialogueEngine.ts`) — this is what satisfies the spec's explicit "독립적인 대사 두 개를 무작위로 이어 붙이지 마" requirement even in the zero-registered-lines case, which is exactly the case that requirement matters most for. If a conversation's registered-line attempt fails partway through (e.g. one speaker has lines but the other doesn't), the partial progress is discarded and one complete default bundle is used for the *entire* exchange instead of a hybrid.
- **Tone-aware text, hand-authored, not string-derived**: every turn carries both a `formal` (존댓말) and `casual` (반말) version (`DefaultDialogueTurnText`), each independently written with correct grammar — never produced by appending "요" or similar, which breaks for plenty of sentence shapes (spec explicitly called this out). `resolveDefaultTurnText` picks based on the *speaking* character's own `tone.baseTone`; `mixed`/`custom` (no single correct register) fall back to the casual variant.
- **Situation categories extended, never renamed** (`situationCategories.ts`): the original 10 ids are untouched (existing registered lines still resolve correctly), with 15 new, more time-of-day-specific ids added for the default library — `wake-up`/`breakfast`/`lunch`/`afternoon-chat`/`snack`/`dinner`/`day-wrap-up`/`pre-bedtime`/`encounter`/`comfort`/`compliment`/`favor`/`gratitude`/`apology`/`muttering`. `muttering` (혼자 중얼거림) is included for completeness against the requested situation list but is **honestly inert** — every dialogue path in this app, auto or manual, is a two-character exchange; there is no solo-speech trigger anywhere, and none was added for this (out of scope — "다른 기능은 추가하지 마").
- **Time-of-day gating is inclusion-based, same principle as the original two gated categories** (`isTimeOfDayEligible`, extended, not replaced): only categories with an actual time implication are hour-gated (e.g. `breakfast` 6-9, `lunch` 11-14, `pre-bedtime`/`bedtime` 21-4) — everything else, including every pre-existing category, stays time-neutral on purpose, so e.g. `casual-chat` remains selectable at night instead of `bedtime` content becoming the *only* thing available then (the spec's explicit "밤이라도 캐릭터가 깨어서 활동 중이라면 무조건 취침 대사만 출력하지 마" requirement — there's no tracked "current activity" state beyond this non-exclusive gating to check against, and this is what makes that honest rather than faked).
- **`conflict`/`reconciliation` have no default content** — both categories were already hard-excluded from auto-dialogue's candidate pool (`AUTO_EXCLUDED_CATEGORIES`, pre-existing, unrelated to this feature) for the same reason as always: no tracked prior-conflict state to make either coherent. Authoring default content there would be permanently unreachable dead content, so none exists.
- **Length preference from personality** (`bundleLengthWeight`): 수다스러움 (talkative) up-weights longer bundles, 과묵함 (reticent) up-weights shorter ones, for either participant — a small, targeted multiplier in `autoDialogueEngine.ts` rather than a new dimension on `PersonalityTagDef`, since the spec names only these two tags for this specific effect. Combined multiplicatively with the existing personality-affinity weight when picking among eligible bundles.
- **Recency**: soft (not hard) — a pair's recently-used bundle ids (`recentDefaultBundleIdsByPair`) are avoided when a fresher eligible bundle exists, but if literally everything eligible has been recently used, the pick still succeeds (repeating) rather than skipping the conversation — the built-in library is generic, repeatable content, unlike a user's own hand-written lines (which *do* get hard-excluded when recently used, falling back only to `isFallback`-marked ones).
- **Never presumes unset user data**: default content never uses a specific family-role address term (오빠/언니/엄마/자기야/etc.) or invents a job/backstory/past event — `defaultDialogueLibrary.test.ts` spot-checks common role words are never present. Family-appropriate warmth comes from universal (unrestricted) bundles reading fine for any relationship, not from presuming a specific role.
- **No relationship-taxonomy change**: the spec's own relationship-effect list mentions "동료" (colleague) as an example, but `RelationshipType` was not extended with a 7th value for it — that would be a schema/logic change beyond this task's two stated problems. Universal (unrestricted) bundles cover both "동료" and "관계 미설정" adequately without one.
- **Test coverage**: `defaultDialogueLibrary.test.ts` validates the content itself structurally (unique ids, valid category references, both tone variants present and actually different, romantic bundles properly restricted, no forbidden address terms, category coverage). `autoDialogueEngine.test.ts`'s new describe block covers the engine-side behavior (fallback triggering, tone resolution, whole-bundle atomicity, romantic/time gating, length bias, recency) against small injected bundle fixtures (`defaultBundleCatalog` param, test-only) rather than the real ~33-bundle catalog, for determinism.

### Autonomous monologue (혼잣말): local, personality/time/behavior-aware, separate from two-person dialogue

Characters occasionally mutter to themselves in a lighter "thought" bubble. No API, no user-registered lines needed. Files live in `features/dialogue/`:

- **Config** (`monologueConfig.ts`): `MONOLOGUE_FREQUENCY_PRESETS` (5 modes `off`/`rare`/`normal`/`frequent`/`veryFrequent` = 끄기/가끔/보통/자주/매우 자주, default `normal`), each with a separate `chancePerTick` (rolled once per 250ms movement tick for an *eligible* character) and `cooldownMs`; `MIN_MONOLOGUE_COOLDOWN_MS` (8s) is a hard floor; `MONOLOGUE_DISPLAY_MS` (5s), `ROOM_ARRIVAL_WINDOW_MS`, `RECENT_MONOLOGUE_HISTORY_SIZE` (8). The "혼잣말 빈도" selector (`LiveScreen.tsx`, `role="group"` labelled "혼잣말 빈도"; the dialogue one is labelled "대화 빈도") is fully independent of "대화 빈도": `'조용히'` only gates character-to-character auto dialogue.
- **Persistence**: only the mode (`monologueFrequencyStore.ts`, key `dearly-monologue-frequency`, missing/corrupt → `normal`). Cooldown timestamps, recent ids, active bubbles and arrival marks are ephemeral in `monologueStore.ts` — kept deliberately separate from `dialogueStore` (`recentAutoLineIdsByCharacter`/`recentDefaultBundleIdsByPair`/`activeBubbleByCharacter` stay two-person-dialogue-only).
- **Library** (`defaultMonologueLibrary.ts`): 152 lines (76 situations × hand-written 반말/존댓말), each with `id`/`text`/`category`/`timeBands`/`personalityTags`/`activities`/`tone`/`weight` (empty condition list = "any"). No questions or response-demanding lines, no assumed backstory, and nothing describing an action the simulation doesn't perform — `monologueEngine.test.ts` checks all of this structurally. Add lines there; keep both registers hand-written.
- **Engine** (`monologueEngine.ts`, pure, injectable `random`/`catalog`): `rollShouldMonologue` (mode gate → that character's own cooldown → per-tick roll × `monologueChanceWeightFor`: 수다스러움 +0.6, 과묵함 −0.5, clamped) and `pickMonologue` (register from `baseTone`, five time bands from `monologueTypes.ts`'s `getMonologueTimeBand`: 05-10 아침 / 11-13 낮 / 14-17 오후 / 18-20 저녁 / 21-04 밤 from the real clock, activity, personality-tag match boosting weight ×(1+2·matches), recent-id exclusion; falls back to fully generic lines, then to `null` = say nothing, never a forced repeat).
- **Activities are real states only** (`monologueTrigger.ts`'s `deriveMonologueActivity`): `roomArrival` (within `ROOM_ARRIVAL_WINDOW_MS` of `completeRoomChange`, which calls `markRoomArrival`), `resting` (`restTicksRemaining > 0`), `wandering` (`status === 'moving'`), else `idle`. `MonologueActivity` also *reserves* `sleeping`/`working`, which the engine's `isMonologueAllowedActivity` blocks — **but neither state exists in the app yet** (no sleep/job system) and nothing produces them; tests only prove the guard, not real sleep/work behavior. When those systems land they just need to report the activity. Furniture *interaction* now exists (see "Furniture interaction: sitting on the sofa" below) — a seated character isn't excluded from monologues (only `'talking'`/busy characters are), it just derives `'idle'` here like any other stationary moment, since sitting isn't itself a distinct `MonologueActivity`; there are still no furniture-use-specific monologue lines (out of scope for this phase, not attempted).
- **Hook point**: `runMonologuePass()` is called at the end of the one existing tick in `useCharacterMovementSimulation.ts` (so it inherits the global pause and adds no timer). It only reads movement state and writes `monologueStore` — it never touches destination/status/room, so it can't interrupt walking or room changes. Expiry is a timestamp check, and the bubble's fade is a CSS animation of the same duration.
- **Priority**: `runConversation` clears both participants' monologues on start; the pass skips/clears anyone `isCharacterBusy` or `'talking'`; `CharacterToken` renders the dialogue bubble *or* the `.character-token-monologue` one (dialogue wins), both through the same `bubbleOffsetUnits` anchor. A monologue follows its character across rooms and, like every token, is only rendered while its character is in the observed room.
- **Not applied**: `firstPerson`/`verbalTic`/`catchphrases` aren't spliced into monologue text (the library is hand-written per register, and nothing is appended to sentences artificially).

  1. Removing a character mid-conversation (`characterStore.removeCharacter`) leaves it as a dangling `dialogueStore.activeConversations` participant until that character's own still-running async `runConversation` naturally finishes (its `finally` calls `endConversation`) — `characterMovementStore` has already dropped the entry by then (`syncCharacterIds`), so the conversation transiently has an unresolvable participant.

  A prior attempt at a proactive fix (eagerly pruning a dangling conversation from `activeConversations` on every tick) was tried and reverted — it created a *worse* race: freeing the still-alive participant to be matched into a brand-new conversation before the old one's async tail finishes, whose delayed `finally` then clobbers the new conversation's status. ### Saved data is loaded defensively: a damaged entry never costs the healthy ones (phase 5)

- **Lists are filtered entry by entry, never all-or-nothing.** `homeStore.ts`'s `usableRooms`/`usablePlacements` (via `usableEntries`) skip anything that isn't an object with the required string ids, keep the first of a repeated id, and treat a non-list as empty; `normalizePlacement` replaces a non-finite/invalid number or a non-string colorway with its default. `characterStore.ts`'s `loadCharacters`/`normalizeDialogueLines` do the same for characters (PNG and every valid line kept verbatim; a missing name/image becomes empty text) and `situationCategoryStore.ts` filters its custom categories. Previously a single `null` entry made `.map(normalize…)` throw, hydration failed silently, and *all* rooms/characters (with their PNGs) were lost. Never add a bare `.map(normalizeX)` over persisted data again. Nothing is capped or deleted for being over a limit (`MAX_ROOMS`/`MAX_CHARACTERS` are enforced when adding, not by discarding saved data).
- **Not persisted, by design**: characters' live positions/rooms/behavior (`characterMovementStore`) and conversation/monologue runtime state regenerate every session; only settings and content are saved.
- **Orphan rescue** (`useCharacterMovementSimulation.ts`): a character whose `roomId` no longer exists (a room removed without `RoomTabs`' relocation flow) is moved to the observed room's doorway (clear of others, via `pickDoorwayArrivalPosition`) instead of being skipped forever.
- **`src/app/integration.test.tsx`** is the whole-app regression net: damaged-save loading, repeat-safe migrations, orphan rescue, a seeded 20-minute five-character/five-room simulation (5 seeds) that checks every tick (rooms exist, positions in bounds, nobody frozen, no double conversations, no monologue while talking, a character removal and a room deletion mid-run), BGM file/registration checks, the one-`new Audio` guard, and an App boot through every screen under StrictMode. `BgmPlayer.test.tsx` swaps `BGM_TRACKS` per test and always restores the shipped list (it no longer assumes an empty catalog).

### Deleting a character or room mid-conversation ends that conversation immediately — never lets its async tail clean up alone

A conversation (`autoDialogueTrigger.ts`'s `runConversation`) is a long-running `async` function that reveals bubbles one at a time over several real seconds and only reaches its own `finally` cleanup (end the conversation, clear both bubbles, reset both participants' movement status/destination) once every line has played out. Deleting a character, or deleting the room a conversation is happening in, both used to leave that cleanup to fire on its own several seconds later — which is too late: `CharacterList`'s delete needs the survivor's bubble/movement freed *now*, and `RoomTabs`'/the orphan-rescue path's relocation needs any conversation state referencing the old room gone *before* `moveCharacterToRoom` runs, not after.

- **`endActiveConversationsFor(characterId)`** (`autoDialogueTrigger.ts`, exported) is the fix: given a character id, it immediately ends every `activeConversations` entry containing that id, clears both participants' bubbles, and resets both to `status: 'idle'`/`destination: null`/`destinationRoomId: null`/`currentBehavior: null` — synchronously, not waiting for `runConversation`'s own timers. Safe to call on a character with no active conversation (no-op) or on an id that no longer exists in `characterMovementStore` (its `updateEntry` helper already no-ops on a missing entry).
- **`runConversation`'s `finally` block is now guarded**: it only performs its own end-conversation/clear-bubble/reset-movement cleanup if `conversationId` is *still* present in `activeConversations` at that point. Without this guard, an `endActiveConversationsFor` call earlier in the same conversation's lifetime — which can, in the time it takes the rest of the bundle to finish revealing, let a freed participant start and even finish a *second* conversation — would let the first conversation's late, unconditional `finally` clobber that unrelated newer state. This was found and reverted as a worse alternative fix first (an eager per-tick `pruneConversationsMissing` that freed a survivor to start a new conversation while the old one's *unguarded* `finally` was still pending, which then stomped the new conversation's state) before landing on the guard + explicit-immediate-cleanup combination described here.
- **Three call sites, all "end the conversation first, relocate/remove second"**: `CharacterList.tsx`'s `handleRemove` (`endActiveConversationsFor` → `monologueStore.forgetCharacter` → `removeCharacter`), `RoomTabs.tsx`'s `confirmDelete` relocation loop (`endActiveConversationsFor` → `moveCharacterToRoom`, per occupant), and `useCharacterMovementSimulation.ts`'s orphan-rescue loop (same order, for a room deleted through some path other than `RoomTabs`' own confirm flow, e.g. a direct `homeStore.removeRoom` call). Getting this order backwards — relocate/remove first — is what left `dialogueStore` thinking a character was still busy in a room or state it no longer occupied.
- **`monologueStore.forgetCharacter(characterId)`** drops that id from all four of `monologueStore`'s per-character maps (`activeByCharacter`, `lastMonologueAtByCharacter`, `recentLineIdsByCharacter`, `lastRoomArrivalAtByCharacter`) — the monologue-side equivalent of ending a conversation, called alongside `endActiveConversationsFor` on character deletion only (a room deletion doesn't remove a character, so its monologue history stays valid).
- **Orchestration lives at the call site, not inside `characterStore`/`homeStore`**, matching the precedent `RoomTabs.tsx` already set by calling `characterMovementStore.moveCharacterToRoom` directly rather than folding relocation into `homeStore.removeRoom` — this also avoids a `characterStore` ↔ `autoDialogueTrigger` circular import.
- **Test coverage**: `src/features/dialogue/conversationCleanup.test.tsx` (new) reproduces both bugs directly (raw, unfixed behavior first, then the fix applied) and covers: active-conversation cleanup right after a character deletion, bubble termination, the survivor's movement resuming (a real tick loop run for 60 ticks, not just a state snapshot), starting a brand-new conversation immediately after, the `finally` guard not clobbering a newer conversation, `forgetCharacter`, the real `CharacterList`/`RoomTabs` UI flows (via `fireEvent`, not `userEvent` — this project's fake-timer test convention), and the orphan-rescue fallback path. `src/app/integration.test.tsx`'s 5-seed stress test exercises a character removal and a room deletion mid-simulation under the same strict per-tick invariants as everything else in that test (no relaxed wait times or loosened assertions for this fix).

### BGM: producer-registered time-of-day music, one shared `<audio>` for the whole app

`src/features/bgm/` — background music the *producer* places in `public/music/` and registers in `bgmConfig.ts`; there is no end-user upload feature, by design (see the main README's "BGM (배경음악) 등록 방법" section for the producer-facing walkthrough).

- **Data model** (`bgmConfig.ts`): `BgmTrackDef` = `{ id, title, fileName, band, order, enabled }`, where `band` is a `TimeBand` (`'morning' | 'daytime' | 'evening' | 'night'`) or `'common'` (a fallback bucket used only when the current band has no track of its own). `BGM_TRACKS` is the one array the producer edits — **empty by default**, since this project ships with no bundled music; nothing was downloaded or invented to fill it, and every part of the system (playlist resolution, the controller, the player UI) is built to handle that empty-list case safely rather than as an afterthought. `resolveMusicUrl(fileName)` turns a bare filename into `${import.meta.env.BASE_URL}music/${fileName}` — Vite's own answer to "what's the app's root right now", so this stays correct if `base` in `vite.config.ts` is ever set for a sub-path deploy (not done in this task — GitHub Pages/deploy work was explicitly out of scope).
- **Time source is deliberately NOT the Live screen's "현재 시간" field** (`timeBand.ts`'s `getCurrentHour()`): that field (`LiveScreen.tsx`'s `time` state) starts from real time but is plain editable text the user can overwrite with anything — treating it as a functional clock would make band detection fragile or simply wrong after any edit. BGM instead reads the same real-system-clock signal (`new Date().getHours()`) already used by `autoDialogueEngine.ts`'s time-of-day line gating and `movementEngine.ts`'s room-choice bias — reusing the app's one genuine real-time source rather than standing up a second, duplicate clock, per the spec's own instruction. `getTimeBand(hour)` is the single shared band-boundary function (아침 05-10, 낮 11-16, 저녁 17-20, 밤 21-04 — the `night` branch is the `else` case, not an explicit range check, so the midnight wrap is correct for free, no seam to get wrong).
- **One shared `<audio>` element, module-scoped, not component-scoped** (`bgmAudioElement.ts`): `export const bgmAudioElement = new Audio()` at module load — constructed exactly once, ever. This is what actually guarantees "오디오 인스턴스는 앱 전체에서 하나만" even under React StrictMode's dev-mode mount→unmount→mount double-invoke: since the element isn't created inside a component or hook body, that double-invoke just adds/removes/re-adds event listeners on the *same* instance (a plain, already-StrictMode-safe `useEffect` cleanup pattern), never constructs a second one. `fadeVolumeTo`/`cancelFade` implement crossfades with a monotonically-increasing "fade token" — a newer fade (or an explicit cancel) invalidates any older in-flight one, which is what stops a stale fade-out from fighting a fresh fade-in's volume after the user rapidly pauses, skips, or the time band changes again mid-transition (spec: "이전 전환 작업이 남아서 음악이 중복 재생되지 않도록"). `playAudio()` never throws — a rejected `.play()` (autoplay block, decode failure, etc.) resolves `{ ok: false, errorName }` for the caller to surface, once, never auto-retried.
- **State split the same way `homeStore`/`dialogueStore` already are** (`bgmStore.ts`): `volume`/`muted`/`bgmEnabled`/`loopEnabled` are `persist`-partialized (localStorage key `dearly-bgm`); `isPlaying`/`currentBand`/`currentTrackId`/`errorMessage` are ephemeral and never persisted — a reload always comes back paused with nothing loaded yet (spec §6), even though the volume/mute/enabled preferences survive. `bgmEnabled` is a master on/off switch distinct from `isPlaying`/pause — turning it off while playing force-pauses and disables the play button; turning it back on never auto-plays (still requires an explicit click, since that's the only autoplay-policy-safe trigger).
- **`bgmActions.ts`** — plain imperative functions (`play`/`pause`/`next`/`previous`/`setVolume`/`toggleMuted`/`toggleBgmEnabled`/`toggleLoopEnabled`), not a hook, same pattern `dialogue/autoDialogueTrigger.ts` already uses: they read/write `bgmStore`/`bgmAudioElement` directly and don't need component lifecycle. `BgmPlayer.tsx`'s click handlers call these; nothing else does.
- **`useBgmController.ts`** — the one hook, mounted exactly once in `App.tsx` (the common layout no phase or room switch ever unmounts), owning: the initial band detection on load (selects, never plays, the first track), a plain `setInterval` real-clock band-check (`BGM_HOUR_CHECK_INTERVAL_MS`, 60s — band transitions only ever happen on the hour, so this doesn't need to be tighter), and the audio element's `ended`/`error` listeners. A detected band change only ever touches playback if something was actually playing — crossfades to the new band's first track if so, otherwise just updates which track is "ready" for the next manual play (spec §4: paused stays paused). If the new band has no track and no `'common'` fallback while playing, it fades out and stops quietly, clearing `currentTrackId` — no error shown, since "no music for this band" isn't a failure. A same-band check is a pure no-op (no reload, no restart) — the gate is a plain equality check against the stored `currentBand` before touching anything. `handleTrackEnded` advances within the current band's playlist (wrapping if `loopEnabled`, stopping after the last track if not) — a single-track band naturally "loops" since next-of-the-only-track is itself. Every band-transition/track-end handler is wrapped end-to-end in try/catch, surfacing failures as `errorMessage` rather than ever letting an exception escape the interval or leave playback half-switched.
- **Screen/room-switch survival needs no special handling at all** — since `useBgmController` lives in `App.tsx` (never unmounted by `phase` changes) and `bgmAudioElement` is a module singleton (never recreated regardless of which components mount/unmount), playback continuing across `SetupScreen`/`DecorateScreen`/`LiveScreen` and across `RoomTabs` room switches is a direct consequence of those two facts, not something `LiveScreen.tsx`/`LiveRoomView.tsx`/`RoomTabs.tsx` needed to know or do anything about — and none of them were touched for this feature.
- **`BgmPlayer.tsx`** — small fixed bar at the bottom of `App.tsx` (pink/cream themed via the existing `--accent`/`--border`/`--panel-bg` tokens), reserving its own space via `App.css`'s `.app-main` bottom padding so it never overlaps content. Every control is a thin wrapper around `bgmActions`/`useBgmStore`; no audio logic lives in the component. Shows "등록된 음악이 없어요" and disables play/prev/next whenever the resolved `currentTrackId` doesn't correspond to a real, currently-enabled `BGM_TRACKS` entry — including the empty-catalog case this project ships with by default.
- **Not built**: any BGM deployment/GitHub Pages work (explicitly out of scope — `resolveMusicUrl` is *ready* for a `base` change, nothing more), a user-facing music upload path (deliberately never built — producer-only registration is the whole point), and a repeat-mode *selector* beyond the single `loopEnabled` on/off toggle (the spec's "반복 설정" persisted field, implemented as one toggle since no richer mode was actually requested).

### PNG export (not currently wired to any button)

`src/engine/export/capturePng.ts` uses PixiJS's `renderer.extract.canvas(app.stage)` to rasterize the current stage and triggers a browser download. It depends on the (currently unused) PixiJS engine, so it won't do anything useful until a `live`-phase scene exists to capture.

### Deployment (GitHub Pages)

No backend by design for the initial version. Deployed as a GitHub Pages *project* site at `https://elpis-for-blanc.github.io/dearly-our-little-life/`, so `vite.config.ts` sets `base: '/dearly-our-little-life/'` to match the actual repo name — without it every built asset request 404s under the real subpath and the page renders blank. If the repo is ever renamed, this must be updated to match. Runtime code that builds its own asset URL (`bgm/bgmConfig.ts`'s `resolveMusicUrl`) already reads `import.meta.env.BASE_URL` rather than hardcoding `/`, so it picks this up automatically — checked project-wide (no other `/`-prefixed absolute asset path exists in `src/`, and there's no router to worry about, see "App flow is phase-based, not routed" above).

## Delivery process for this project

Work is done phase by phase, not as one large implementation:

1. Implement one phase's slice of functionality.
2. Check it doesn't conflict with previously implemented phases (shared stores/engine state).
3. Verify with `npm run build`, `npm run lint`, and `npm run test`.
4. Verify visually in an actual browser before calling UI work done — if no browser-testing tool is available in the session, say so explicitly rather than claiming visual verification happened.
5. Report the result before moving to the next phase.

No throwaway/temporary patches — implement each phase to the same standard as the rest of the codebase. Never leave a debugging change (a flipped default phase, seeded fake store data, etc.) committed — if you temporarily mutate state to inspect something, revert it in the same turn before doing anything else.
